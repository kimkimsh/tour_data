# 03 — 첫 데이터 수집

> **끝나면:** 화면의 「정보 없음」이 실제 값으로 바뀐다.
> **걸리는 시간:** 1–2시간. 그중 대부분은 **4단계에서 사람이 문장을 읽는 시간**이다.
> **필요한 것:** [`01_kto_api_key.md`](./01_kto_api_key.md) 완료. Supabase는 없어도 된다.

---

## 순서가 정해져 있다

각 단계가 앞 단계의 결과를 쓴다. **건너뛰면 그다음이 틀린 값으로 돈다.**

```
1. pnpm probe              →  관광지 6곳의 진짜 id를 알아낸다
2. pois.json 고치기         →  그 id를 코드에 넣는다
3. pnpm validate:content   →  여기서 초록불이 되어야 다음으로 간다
4. pnpm ingest --dry-run   →  ★ 사람이 문장 144개를 눈으로 본다
5. pnpm ingest             →  진짜 수집
```

---

## 1단계 — probe: 관광지 6곳의 진짜 id 알아내기

```bash
pnpm probe
```

### 이게 왜 필요한가

한국관광공사 데이터에서 관광지 하나하나는 **`contentId`라는 숫자**로 구분된다. 「공산성」이라는 이름으로는 못 부르고 그 숫자로만 부를 수 있다.

지금 `content/pois.json`에는 그 자리에 **`"UNRESOLVED"`**라고 적혀 있다:

```json
{
  "slug": "gongsanseong",
  "nameKo": "공산성",
  "ktoContentId": "UNRESOLVED",   ← 이것
  ...
}
```

**모른다고 적어 둔 것이다.** 이전 기획 문서에 서로 다른 id 세 벌이 있었는데 어느 것이 맞는지 확인할 방법이 없어서, 셋 다 쓰지 않고 「모른다」를 넣었다.

**틀린 id를 넣으면 조용히 엉뚱한 관광지의 데이터를 수집한다.** 오류도 안 나고 화면도 정상으로 보인다 — 내용만 남의 것이다. 그게 이 서비스가 절대 하면 안 되는 종류의 실패라서, 확인될 때까지 배포를 막아 두었다.

### 결과 읽기

`docs/spec/_probe-results.md` 파일이 새로 쓰인다. 이 안에 **6곳의 진짜 `contentId`**가 있다.

**P0-1이 제일 중요한 줄이다.** 「이 6곳이 무장애 여행 데이터셋에 등록돼 있는가」에 답한다.

| P0-1의 답 | 뜻 | 다음에 할 일 |
|---|---|---|
| 6곳 다 등록 | 무장애 항목 24개가 채워진다 | 그대로 진행 |
| 일부만 등록 | 등록된 곳만 채워진다 | 그대로 진행 |
| **한 곳도 없음** | **무장애 항목이 전부 「정보 없음」으로 남는다** | 나한테 알려 달라 — 프로젝트 방향을 바꿔야 한다 |

마지막 줄이 나오면 적합도 점수는 보여 줄 게 없어지고, **대신 갭 리포트(「무엇이 비어 있는가」)가 주 화면이 되어야 한다.** 그건 코드를 다시 배치하는 일이라 혼자 정할 수 없다.

---

## 2단계 — pois.json 고치기

`content/pois.json`을 열고, 6곳의 `"UNRESOLVED"`를 probe가 알려 준 숫자로 바꾼다.

```json
"ktoContentId": "UNRESOLVED",     ← 이렇게 되어 있는 것을
"ktoContentId": "126508",         ← 이렇게 (실제 숫자는 probe 결과를 본다)
```

**따옴표는 그대로 둔다.** 숫자로 보여도 문자열로 다룬다.

6곳 전부 바꿔야 한다: `gongsanseong`, `muryeong-royal-tombs`, `gongju-national-museum`, `busosanseong`, `jeongnimsaji`, `buyeo-national-museum`.

## 3단계 — 확인

```bash
pnpm validate:content
```

**여기서 초록불이 나와야 다음으로 간다.** 지금까지 빨간불이던 게 이 단계에서 풀린다.

아직 빨간불이면 6곳 중 안 바꾼 게 있다 — 메시지에 어느 곳인지 이름이 나온다.

이게 초록불이 되면 **CI도 같이 초록불이 된다.**

## 4단계 — ★ 가장 중요한 단계: 문장 144개 눈으로 보기

```bash
pnpm ingest --dry-run
```

`--dry-run`은 **파일만 쓰고 데이터베이스는 건드리지 않는다.** 결과를 먼저 보고 판단하기 위한 것이다.

### 무엇을 보는 것인가

한국관광공사는 무장애 정보를 **`Y/N`이 아니라 한국어 문장으로** 준다:

```
"대여가능(수동휠체어 2대)"
"출입구까지 경사로가 설치되어 있음"
"계단만 있음"
""
```

이 문장을 읽어서 `있음 / 일부 / 없음 / 모름` 넷 중 하나로 바꾸는 함수가 있다(`resolveStatus`). **이 함수가 이 프로젝트에서 제일 위험한 곳이다.**

왜냐하면 문장 → 판정으로 바뀌는 지점이 여기 하나뿐이고, **그 뒤의 모든 숫자가 이 판정을 물려받기** 때문이다. 여기서 한 번 틀리면 점수도, 라벨도, 「확인 필요」 목록도, 갭 리포트도 전부 같이 틀린다.

### 실제로 두 번 틀렸다

| 문장 | 잘못 판정한 값 | 맞는 값 |
|---|---|---|
| `계단만 있음` | **있음** ← 계단뿐인데 「엘리베이터 있음」으로 찍혔다 | 없음 |
| `엘리베이터 없음` | **모름** ← 확인된 장벽인데 「확인 필요」로 찍혔다 | 없음 |

첫 줄이 왜 나왔냐면, 규칙이 `있음`이라는 단어를 **문장 어디서든** 찾았기 때문이다. 둘째 줄은 그걸 고치면서 `없음`을 아예 안 보게 만들었기 때문이다.

지금은 **부정어가 어느 단어 옆에 붙었는지**를 본다. `단차 없음`(장애물이 없다 → 좋음)과 `엘리베이터 없음`(시설이 없다 → 나쁨)을 구분하려면 그 방법밖에 없다.

### 그래서 사람이 봐야 한다

회귀 테스트 42건을 붙여 뒀지만, **그 42건은 우리가 이미 아는 문장이다.** 6곳 × 24항목 = **144개의 실제 문장**에는 본 적 없는 표현이 있다.

`content/generated/accessibility.json`을 열고 **원문(`detail`)과 판정(`status`)을 나란히 본다.**

이렇게 보면 편하다:

```bash
python3 -c "
import json
for f in json.load(open('content/generated/accessibility.json')):
    if f['detail']:
        print(f\"{f['status']:12} | {f['detail']}\")
" | sort | uniq
```

**한 줄씩 읽으면서 「이 문장에 이 판정이 맞나」만 본다.**

### 이런 것을 찾는다

- **장애물 단어가 빠졌나** — 지금 아는 단어: `단차` `문턱` `계단` `장애물` `급경사` `경사`(단, `경사로`는 제외) `돌길` `자갈` `비포장` `협소` `좁음`. 실제 문장에 다른 표현이 있으면 알려 달라
- **부정어가 너무 멀리 있나** — 단어에서 **8글자 안**만 본다. `단차가 거의 없는 편입니다` 같은 문장은 그 범위를 넘길 수 있다
- **`어려움`을 「일부」로 읽는 게 맞나** — `진입 어려움`을 지금은 「일부 가능」으로 읽는데, 문맥에 따라 「불가」가 맞을 수도 있다

### 틀린 게 나오면

두 가지 방법이 있다:

**A. 규칙을 고친다** — 같은 표현이 여러 곳에 나올 때. 나한테 그 문장을 보여 주면 규칙에 반영하고 테스트에 추가한다.

**B. 그 한 줄만 손으로 덮어쓴다** — 한 곳에만 나오는 특이한 문장일 때. `content/curated-facts.json`에 출처와 확인 날짜를 붙여 한 줄 추가하면 그게 이긴다.

## 5단계 — 진짜 수집

문장 대조가 끝났으면:

```bash
pnpm ingest
```

Supabase가 연결돼 있으면 데이터베이스에도 쓰고, 없으면 파일에만 쓴다. **둘 다 정상 동작이다.**

### 이때 나올 수 있는 경고

**`no weather source is wired`** — 기상 특보는 아직 붙인 데가 없다. 32개 항목 중 하나가 계속 「정보 없음」으로 남는다. **의도된 것이고 결정이 필요한 사안이다** ([`../work_log/04_open_items.md`](../work_log/04_open_items.md) §3.1).

**`daily quota reached`** — 하루 한도(오퍼레이션당 1,000건)를 넘었다. **이 경우 아무것도 저장하지 않고 멈춘다.** 절반만 저장하면 다음 날 「데이터가 있다」고 판단해서 나머지를 영영 안 가져오기 때문이다. 내일 다시 돌리면 된다.

**`Odii themeBasedList failed`** — 도슨트(음성 안내)를 못 가져왔다. 그 화면만 비고 나머지는 정상이다.
