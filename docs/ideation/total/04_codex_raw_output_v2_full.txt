# Brainstorming Ideas Into Designs

Help turn ideas into fully formed designs and specs through natural collaborative dialogue.

Start by understanding the current project context, then ask questions one at a time to refine the idea. Once you understand what you're building, present the design and get user approval.

<HARD-GATE>
Do NOT invoke any implementation skill, write any code, scaffold any project, or take any implementation action until you have presented a design and the user has approved it. This applies to EVERY project regardless of perceived simplicity.
</HARD-GATE>

## Anti-Pattern: "This Is Too Simple To Need A Design"

Every project goes through this process. A todo list, a single-function utility, a config change — all of them. "Simple" projects are where unexamined assumptions cause the most wasted work. The design can be short (a few sentences for truly simple projects), but you MUST present it and get approval.

## Checklist

You MUST create a task for each of these items and complete them in order:

1. **Explore project context** — check files, docs, recent commits
2. **Offer visual companion** (if topic will involve visual questions) — this is its own message, not combined with a clarifying question. See the Visual Companion section below.
3. **Ask clarifying questions** — one at a time, understand purpose/constraints/success criteria
4. **Propose 2-3 approaches** — with trade-offs and your recommendation
5. **Present design** — in sections scaled to their complexity, get user approval after each section
6. **Write design doc** — save to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md` and commit
7. **Spec self-review** — quick inline check for placeholders, contradictions, ambiguity, scope (see below)
8. **User reviews written spec** — ask user to review the spec file before proceeding
9. **Transition to implementation** — invoke writing-plans skill to create implementation plan

## The Process

**Understanding the idea:**

- Check out the current project state first (files, docs, recent commits)
- Before asking detailed questions, assess scope: if the request describes multiple independent subsystems (e.g., "build a platform with chat, file storage, billing, and analytics"), flag this immediately. Don't spend questions refining details of a project that needs to be decomposed first.
- If the project is too large for a single spec, help the user decompose into sub-projects: what are the independent pieces, how do they relate, what order should they be built? Then brainstorm the first sub-project through the normal design flow. Each sub-project gets its own spec → plan → implementation cycle.
- For appropriately-scoped projects, ask questions one at a time to refine the idea
- Prefer multiple choice questions when possible, but open-ended is fine too
- Only one question per message - if a topic needs more exploration, break it into multiple questions
- Focus on understanding: purpose, constraints, success criteria

**Exploring approaches:**

- Propose 2-3 different approaches with trade-offs
- Present options conversationally with your recommendation and reasoning
- Lead with your recommended option and explain why

**Presenting the design:**

- Once you believe you understand what you're building, present the design
- Scale each section to its complexity: a few sentences if straightforward, up to 200-300 words if nuanced
- Ask after each section whether it looks right so far
- Cover: architecture, components, data flow, error handling, testing
- Be ready to go back and clarify if something doesn't make sense

**Design for isolation and clarity:**

- Break the system into smaller units that each have one clear purpose, communicate through well-defined interfaces, and can be understood and tested independently
- For each unit, you should be able to answer: what does it do, how do you use it, and what does it depend on?
- Can someone understand what a unit does without reading its internals? Can you change the internals without breaking consumers? If not, the boundaries need work.
- Smaller, well-bounded units are also easier for you to work with - you reason better about code you can hold in context at once, and your edits are more reliable when files are focused. When a file grows large, that's often a signal that it's doing too much.

**Working in existing codebases:**

- Explore the current structure before proposing changes. Follow existing patterns.
- Where existing code has problems that affect the work (e.g., a file that's grown too large, unclear boundaries, tangled responsibilities), include targeted improvements as part of the design - the way a good developer improves code they're working in.
- Don't propose unrelated refactoring. Stay focused on what serves the current goal.

## After the Design

**Documentation:**

- Write the validated design (spec) to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`
  - (User preferences for spec location override this default)
- Use elements-of-style:writing-clearly-and-concisely skill if available
- Commit the design document to git

**Spec Self-Review:**
After writing the spec document, look at it with fresh eyes:

1. **Placeholder scan:** Any "TBD", "TODO", incomplete sections, or vague requirements? Fix them.
2. **Internal consistency:** Do any sections contradict each other? Does the architecture match the feature descriptions?
3. **Scope check:** Is this focused enough for a single implementation plan, or does it need decomposition?
4. **Ambiguity check:** Could any requirement be interpreted two different ways? If so, pick one and make it explicit.

Fix any issues inline. No need to re-review — just fix and move on.

**User Review Gate:**
After the spec review loop passes, ask the user to review the written spec before proceeding:

> "Spec written and committed to `<path>`. Please review it and let me know if you want to make any changes before we start writing out the implementation plan."

Wait for the user's response. If they request changes, make them and re-run the spec review loop. Only proceed once the user approves.

**Implementation:**

- Invoke the writing-plans skill to create a detailed implementation plan
- Do NOT invoke any other skill. writing-plans is the next step.

## Key Principles

- **One question at a time** - Don't overwhelm with multiple questions
- **Multiple choice preferred** - Easier to answer than open-ended when possible
- **YAGNI ruthlessly** - Remove unnecessary features from all designs
- **Explore alternatives** - Always propose 2-3 approaches before settling
- **Incremental validation** - Present design, get approval before moving on
- **Be flexible** - Go back and clarify when something doesn't make sense

## Visual Companion

A browser-based companion for showing mockups, diagrams, and visual options during brainstorming. Available as a tool — not a mode. Accepting the companion means it's available for questions that benefit from visual treatment; it does NOT mean every question goes through the browser.

**Offering the companion:** When you anticipate that upcoming questions will involve visual content (mockups, layouts, diagrams), offer it once for consent:
> "Some of what we're working on might be easier to explain if I can show it to you in a web browser. I can put together mockups, diagrams, comparisons, and other visuals as we go. This feature is still new and can be token-intensive. Want to try it? (Requires opening a local URL)"

**This offer MUST be its own message.** Do not combine it with clarifying questions, context summaries, or any other content. The message should contain ONLY the offer above and nothing else. Wait for the user's response before continuing. If they decline, proceed with text-only brainstorming.

**Per-question decision:** Even after the user accepts, decide FOR EACH QUESTION whether to use the browser or the terminal. The test: **would the user understand this better by seeing it than reading it?**

- **Use the browser** for content that IS visual — mockups, wireframes, layout comparisons, architecture diagrams, side-by-side visual designs
- **Use the terminal** for content that is text — requirements questions, conceptual choices, tradeoff lists, A/B/C/D text options, scope decisions

A question about a UI topic is not automatically a visual question. "What does personality mean in this context?" is a conceptual question — use the terminal. "Which wizard layout works better?" is a visual question — use the browser.

If they agree to the companion, read the detailed guide before proceeding:
`skills/brainstorming/visual-companion.md`

## 1) 서비스 기획배경 및 필요성

### 1.1 서비스 기획 배경

**한국 무장애 관광 인프라는 "POI 단위 정적 인증"에 머물러 있다.** KTO 「모두의 여행」, Wheelmap, Wheelmate는 모두 "이 관광지가 휠체어 진입 가능한가"라는 단일 POI 질문에 멈춘다. 그러나 휠체어 사용자·유아차 동반 가족·시각장애인·외국인이 실제 백제역사유적지구를 방문할 때 마주치는 질문은 다음 5개다:

1. **여러 유적이 단차 없이 이어지는 1박 2일 동선이 있는가** — 한 곳만 접근 가능해서는 의미가 없다.
2. **현장에 가보니 엘리베이터가 고장났다면 다음 사용자도 알 수 있는가** — 엘리베이터·경사로 정적 정보의 60% 이상이 6개월 이상 미갱신 상태다.
3. **자녀가 백제 역사를 이해하고 학교에 제출할 체험학습 자료를 만들 수 있는가** — 휠체어 자녀를 둔 가족·일반 자녀 동반 가족 공통의 페인포인트.
4. **외국인이 다국어 GPS 오디오로 백제를 이해할 수 있는가** — 현재 부여 부소산성·공주 공산성에 위치 트리거 다국어 오디오 도슨트는 운영되지 않는다.
5. **충남 RTO·지자체가 "어느 시군의 무장애 정보가 부족한가"를 데이터로 볼 수 있는가** — KorWithService2 detailWithTour2 누락 POI 시각화 도구가 한국에 없다.

세 가지 정책 흐름이 동시에 같은 방향을 가리킨다 — (a) **고령화** : 65세 이상 1,000만 명 돌파(2025), 시니어 관광 시장 +20%/yr, (b) **AI 기본법(2026.1.22 시행)** : 생성형 AI 결과물 표시·접근성 의무, (c) **KWCAG 2.2 + 디지털포용법 + 장차법 제20·21조** : 정보접근권은 권고에서 의무로 전환되는 추세.

## 2) 서비스 개요

### 2.1 기획 서비스 소개 (한 줄)

> **휠체어·유아차·시각장애·외국인이 모두 갈 수 있는 충남 공주·부여 백제역사유적지구의 무장애 동선·다국어 GPS 도슨트·체험학습 다이어리·현장 검증을 한 화면에 묶은 무장애 헤리티지 관광 OS — 「모두의 백제 (Modu Baekje)」**

### 2.2 기획 서비스 주요 기능 (5개 핵심 — MVP)

#### F1. 무장애 적합도 카드 + 1박 2일 동선 빌더

- **입력 (4 페르소나 프로필)** : P1 휠체어·시니어(장시간 보행 어려움) / P2 시각장애·청각장애·도우미견 / P3 유아차·초등 자녀 동반 / P4 교사·복지기관 단체 인솔자 (단체 인원·다양한 제약 교집합) — 외국인 4언어는 별도 토글. 페르소나는 다중 선택 가능 (예: 휠체어 시니어 + 손녀 동반).
- **출력** : 공주(공산성·무령왕릉과 왕릉원·국립공주박물관·송산리고분군·공주 한옥마을) + 부여(부소산성·정림사지·국립부여박물관·능산리고분군·궁남지) 후보 POI 각각에 대해 **방문 가능 / 주의 필요 / 정보 없음(현장 확인 필요) / 대체 추천** 4단계 카드.
- **무장애 적합도 점수 (가중치)** :

```
적합도 = 0.40 × 진입 가능성   (KorWithService2 detailWithTour2 — wheelchair / exit / elevator)
       + 0.20 × 동선 연속성   (이전·다음 POI까지 무장애 경로 + 카카오맵 경사도)
       + 0.20 × 편의시설 충족 (restroom · auditorium · room · lactationroom · stroller)
       + 0.10 × 시간대 적합도 (TatsCnctrRate — 백제문화제·야간관광 기간 휠체어 회전)
       + 0.10 × UGC 검증     (최근 30일 사용자 신고 가중)
```

- **fallback 추천** : 적합도 70% 미만 POI는 같은 테마 인접지로 자동 대체 (KorService2 lclsSystmCode2 + TarRlteTarService1 활용).
- **1박 2일 / 당일 두 모드** : 시간 예산 + 야간관광 옵션(공산성 야경·금강·부여 야시장)으로 분기.

#### F2. GPS 트리거 다국어 오디오 도슨트 (Odii 활용)

- **위치 진입 시 자동 재생** — Odii.storyLocationBasedList(`xCoord`/`yCoord`/`radius`)로 반경 진입 시 백제 스토리 오디오·자막 자동 호출.
- **2 모드 분리** : 어린이 모드(쉬운 말, 퀴즈 연동) / 어른 모드(전문 해설, 국가유산청 메타데이터 결합).
- **다국어 4종** : 국문(KorService2) + 영문(EngService2) + 일문(JpnService2) + 중문 간체(ChsService2) — KTO 다국어 원문 우선, 보조 번역은 "AI 음성 안내" 표기 (AI 기본법 2026.1.22 대응).
- **시각장애 우선** — TalkBack/VoiceOver 100% 호환, 큰 글씨·고대비 모드 동시 제공.

#### F3. 현장 배리어 제보 + 자동 코스 재계산 (Waze 패턴 UGC)

- 사용자가 엘리베이터 고장·공사 구간·임시 폐쇄·화장실 이용 불가를 사진+위치 제보.
- 같은 코스 후속 사용자에게 푸시 알림.
- 같은 위치 24시간 내 3건 이상 신고 → 코스 자동 재계산 (TarRlteTarService1 인접 대체지 추천).
- 위치정보법 제9조에 따라 **위치기반서비스사업자 신고** 완료 후 운영, GPS 동의서 별도 명시 (PIPA 처리방침).

#### F4. 체험학습 다이어리 PDF (자녀 학습 모드)

- **방문 인증** : QR 또는 GPS 진입 검증.
- **사진 + 퀴즈 + 음성 메모** : Odii 어린이 모드 스토리에서 자동 생성된 백제 퀴즈 풀고, 사진 첨부, 음성 메모 녹음.
- **학교 제출용 PDF 즉시 출력** : 방문지·이동 시간·학습 내용·아동 소감 — 학교 양식과 동일 구조.
- **PT 시연 핵심 장면** — 가족·학교·복지기관 누구나 즉시 이해 가능한 실용 기능.

#### F5. RTO 데이터 갭 리포트 (충남 CACF 대시보드, B2G)

- detailWithTour2 누락 POI 자동 식별 → "공주 시 무장애 정보 입력 누락 12건 / 부여 군 9건" 시각화.
- 사용자 제보 빈도 + UGC 검증 결과 → **접근성 개선 후보지 시군구별 히트맵** (lDongSignguCd 기준).
- 일/주/월 리포트 자동 생성 → 충남문화관광재단(CACF) + 다도라 / 올담 데이터포털과 정기 공유.
- **B2G 가치를 발전성 점수(20점)로 직결**.

### 2.3 서비스 차별성

KTO 「모두의 여행」·Wheelmap·Wheelmate가 멈춘 **POI 단위 정적 인증**을 본 서비스는 **5축 통합**으로 끌어올린다 — (1) **동선** : 4 페르소나 적합도 카드 + 1박 2일 빌더, (2) **다국어 GPS 도슨트** : Odii 위치기반 자동 재생, (3) **실시간 검증** : Waze 패턴 24시간 내 3건 자동 재계산, (4) **체험학습 다이어리 PDF** : 학교·가족 직접 시연 가능한 PT 무기, (5) **B2G 데이터 갭 리포트** : 충남 RTO에 즉시 가치 제공.

> **5축 중 가장 강한 차별축 = (4) 체험학습 다이어리 PDF.** 동선·혼잡·UGC는 데이터 활용 적절성 점수(20점)를 만들고, 다이어리는 **PT 발표에서 즉시 이해되는 "결과물"** 이다. 다른 POI 조회형 무장애 앱과 결정적으로 갈라지는 지점은 — **"무장애 여행이 자녀의 교육 산출물로 남는다"** — 한 문장으로 압축된다. 적정성·실용성·발표 3개 점수(70점)를 동시에 끌어올린다.

**KorWithService2 detailWithTour2 + Odii GPS 트리거 + 다국어 4종(국·영·일·중) + DataLab/TatsCnctr + PhotoGallery**의 6축 결합 사례는 **한국 0**이며, "유네스코 백제 + KWCAG 2.2 + AI 기본법 + 충남 RTO B2G" 4축은 PT 적정성 점수(30점) 직격.

### 2.4 서비스 내 지역 특화 (충남 — 필수 항목)

**왜 충남 단일인가** :
- **백제역사유적지구(유네스코 세계유산)** — 공주(공산성·송산리 고분군·정지산 유적) + 부여(관북리 유적·부소산성·정림사지·능산리 고분군·나성) — 명확한 헤리티지 IP.
- **공주 야간관광 특화도시** — 공산성 야경·금강·부여 야시장을 야간 모드 핵심 콘텐츠로 그대로 흡수.
- **다도라(DADORA)** — 충남 스마트관광 전자지도 SaaS, 본 서비스의 RTO 갭 리포트와 자연스럽게 통합 가능.
- **올담(alldam)** — 충남 데이터포털, 공주·부여 시군 무장애 보조 데이터 보강.
- **충남은 2026 공모전 RTO 특별상 8개 권역(부산·대전·광주·세종·충남·경북·강원·제주) 중 하나** (info.pdf p.6) — 단일 지역 한정 출시 시 가점 +2 + CACF 특별상 후보.

**왜 경북 / 다른 RTO를 선택하지 않는가** : 경북은 메타버스/XR 강점이지만 4개월 안에 AR 콘텐츠 제작 리스크 큼. 제주는 자체 OpenAPI(REST+SPARQL)가 풍부해 KTO API 활용 차별성이 약화됨. 충남은 KTO API 의존도 중간 + 명확한 유네스코 IP + 야간관광 특화도시 + 다도라/올담 RTO 협력 자산 = **무장애 헤리티지에 가장 정합적**.

**MVP 대상 6 POI (공주·부여 각 3)** :
- **공주** : 공산성(史 477) / 무령왕릉과 왕릉원(史 13) / 국립공주박물관
- **부여** : 부소산성(史 5) / 정림사지(史 301) + 정림사지박물관 / 국립부여박물관

**확장 후보 (발전방향)** : 공주 한옥마을·송산리 고분군 / 부여 능산리 고분군·궁남지·백제문화단지 / 익산(미륵사지·왕궁리 유적) / 논산.

### 3.2 데이터 활용 방식

#### (1) F1 적합도 카드 — KorWithService2 detailWithTour2 21필드 직접 활용

매뉴얼 (`docs/api_manual/1737596514908/한국관광공사_개방데이터_활용매뉴얼(무장애여행)_v4.3.docx`) 응답 필드 직인용 :

| 카테고리 | 응답 필드 (영문 키) | 본 서비스에서의 의미 |
|---|---|---|
| **공통 5** | `parking` · `route` · `publictransport` · `ticketoffice` · `promotion` | 주차·접근로·대중교통·매표소·홍보물 무장애 |
| **지체장애 7** | `wheelchair` · `exit` · `elevator` · `restroom` · `auditorium` · `room` · `handicapetc` | 휠체어 임대·출입구·엘리베이터·장애인 화장실·관람석·전용 객실 |
| **시각장애 7** | `braileblock` · `helpdog` · `guidehuman` · `audioguide` · `bigprint` · `brailepromotion` · `guidesystem` (+ `blindhandicapetc`) | 점자블록·도우미견·안내인·오디오 가이드·큰 글씨·점자 안내·안내 시스템 |
| **청각장애 4** | `signguide` · `videoguide` · `hearingroom` · `hearinghandicapetc` | 수어 안내·영상 안내·청각 보조 객실 |
| **영유아가족 3** | `stroller` · `lactationroom` · `babysparechair` (+ `infantsfamilyetc`) | 유아차 임대·수유실·유아 의자 |

**호출 예시** (공주시 부소산성 무장애 상세 — `contentId=988449`는 매뉴얼 샘플 ID, 운영 시 실제 ID로 치환) :

```
GET https://apis.data.go.kr/B551011/KorWithService2/detailWithTour2?
    serviceKey={KEY}&MobileOS=ETC&MobileApp=ModuBaekje&_type=json&contentId=988449
```

**중요 — 신구 코드 체계 전환** : KorWithService2의 `areaCode2` / `categoryCode2` 오퍼레이션과 legacy `areaCode` / `sigunguCode` / `cat1` / `cat2` / `cat3` 파라미터는 **2025-12-31까지만 활용 가능** (매뉴얼 § areaCode2 명시). 본 서비스는 2026년 출시이므로 **`ldongCode2` + `lclsSystmCode2` 신규 체계만 사용**한다.

#### (2) F1 동선 빌더 — KorService2 신분류체계 정밀 검색

충남 공주·부여 백제 유적의 lclsSystm 분류 매핑 (매뉴얼 부속 `신분류체계정보 관광타입정보 연계 정의서.xlsx` 직인용) :

| 카테고리 | lclsSystm1 | lclsSystm2 | lclsSystm3 (예시) | contentTypeId |
|---|---|---|---|---|
| 공산성·부소산성·무령왕릉 | `HS` 역사관광 | `HS01` 역사유적지 | (12개 소분류 중 매칭) | 12 (관광지) |
| 정림사지 등 종교성지 | `HS` | `HS03` 종교성지 | (4개) | 12 |
| 국립공주박물관·국립부여박물관 | `VE` 문화관광 | `VE07` 전시시설 | (6개) | 14 (문화시설) |
| 백제문화제 | `EV` 축제 | `EV01` 축제 | `EV010100` 문화관광축제 | 15 (축제) |
| 백제관·한옥스테이 (숙박) | `AC` 숙박 | `AC03` 펜션/민박 | `AC030200` 한옥스테이 | 32 (숙박) |

호출 예시 (공주시 — `lDongRegnCd=44` 충청남도 + `lDongSignguCd=150` 공주시) :

```
GET https://apis.data.go.kr/B551011/KorService2/areaBasedList2?
    serviceKey={KEY}&MobileOS=ETC&MobileApp=ModuBaekje&_type=json
    &lDongRegnCd=44&lDongSignguCd=150&lclsSystm1=HS&lclsSystm2=HS01
    &contentTypeId=12&arrange=C&numOfRows=50
```

**KorWithService2 contentTypeId 제약** : 매뉴얼 § 무장애 안내 — 무장애 서비스는 **12 / 14 / 15 / 28 / 32 / 38** 6종만 지원 (음식점 39 · 여행코스 25 미지원). 본 서비스는 식음료 무장애 정보를 KorService2 39 (음식점) `chkbabycarriage`(유모차 대여), `kidsfacility`(어린이놀이방) 필드로 보강한다.

#### (3) F2 GPS 트리거 다국어 도슨트 — Odii 위치기반

매뉴얼 (`docs/api_manual/1720672146251/한국관광공사_개방데이터_활용매뉴얼(오디)_v4.1.docx`) 특이 사항 :

- **좌표 파라미터 명이 다른 서비스와 다름** — `xCoord` / `yCoord` (KorService2의 `mapX` / `mapY`가 아님).
- **`langCode` 파라미터** — `ko` / `en` / `ja` / `zh-CN` 등으로 다국어 분기.
- **신분류체계(lclsSystm) 미사용** — 자체 `themeNm` 등 코드 체계 활용.

호출 예시 (공주 공산성 진입 시 영어 백제 스토리 자동 호출) :

```
GET https://apis.data.go.kr/B551011/Odii/storyLocationBasedList?
    serviceKey={KEY}&MobileOS=ETC&MobileApp=ModuBaekje
    &langCode=en&xCoord=127.1247&yCoord=36.4654&radius=500
```

#### (4) F2 외국인 다국어 카드 — 4언어 contentTypeId 매핑

다국어 매뉴얼은 contentTypeId 코드 체계가 국문과 다르다 — **국문 12(관광지) ↔ 다국어 76**, **국문 14(문화시설) ↔ 다국어 78**, **국문 15(축제) ↔ 다국어 85**, **국문 32(숙박) ↔ 다국어 80** (다국어 v4.4 매뉴얼 § Table 4 직인용). 본 서비스는 외국인 모드 진입 시 자동 매핑 변환을 거쳐 EngService2 / JpnService2 / ChsService2 호출.

#### (5) F1 시간대 적합도 + 야간관광 — TatsCnctrRateService

매뉴얼 § `tatsCnctrRateList` 직인용 — `areaCd` (legacy 지역코드, 충남=34) + `signguCd` (예: 부여 34800) + `tAtsNm` (관광지명) 기반 향후 30일 집중률.

```
GET https://apis.data.go.kr/B551011/TatsCnctrRateService/tatsCnctrRateList?
    serviceKey={KEY}&MobileOS=ETC&MobileApp=ModuBaekje
    &areaCd=34&signguCd=34800&tAtsNm=부소산성
```

> 주의 — TatsCnctrRateService는 매뉴얼 기준 legacy areaCd / signguCd를 사용한다. lDong 5자리 체계가 아닌 별도 코드 체계임. 본 서비스는 두 체계 매핑 테이블을 내부 유지.

#### (6) F5 RTO 대시보드 — DataLabService 일일 방문자

매뉴얼 § `locgoRegnVisitrDDList` 직인용 — `startYmd` / `endYmd` (YYYYMMDD) 필수. KT 내국인 + SK텔레콤 외국인 이동통신 기반. 매뉴얼이 명시한 한계 — **"방문 목적을 정확히 알 수 없으므로 '방문자'는 '관광객'과 동일하게 정의되지 않음"**. 본 서비스는 이 한계를 화면에 명시하고 추세 분석 보조로만 사용한다.

#### (7) 라이선스·표시 의무

- **공공누리 출처 표시** — KorService2/KorWithService2의 `cpyrhtDivCd`가 `Type1`(제1유형 — 출처표시) 또는 `Type3`(제1유형 + 변경금지)로 반환. 화면에 출처 자동 표기.
- **AI 표시 의무** (AI 기본법 2026.1.22 시행) — Odii TTS 보조·번역·동선 자동 생성 시 "AI 음성 안내 / AI 생성 코스" 배지.
- **위치정보법 제9조** — 위치기반서비스사업자 신고 (방통위) + GPS 동의서 별도 명시.

## 부록 D. PT 시연 시나리오

### D.1 핵심 시연 — "휠체어 할아버지와 초등 손녀의 공산성"

> **무대 설정** — 휠체어 사용 70대 할아버지와 초등학생 손녀가 공주 공산성에 도착했다.
>
> 1. **앱 진입 / KWCAG 2.2 자체 구현 시연** — 휠체어 모드 + 손녀의 어린이 모드를 다중 선택. 명도 4.5:1, 터치 44pt, TalkBack 호환을 즉석에서 보여준다.
> 2. **F1 적합도 카드 + 동선 자동 재구성** — 공산성·무령왕릉과 왕릉원·국립공주박물관 동선의 휠체어 적합도를 카드로 표시. 어제 들어온 "공산성 동문 진입로 공사 중" 제보가 자동 검증되어, 동선이 서문 진입 + 평탄 구간 위주로 자동 재계산된다.
> 3. **F2 GPS 트리거 Odii 도슨트** — 공산성 진입 GPS 트리거 발동, 손녀 어린이 모드 백제 스토리 자동 재생.
> 4. **F4 체험학습 다이어리 PDF** — 손녀가 퀴즈 3문항을 풀고, 할아버지와 함께 찍은 사진을 첨부, 음성 메모로 "할아버지가 들려주신 무령왕 이야기"를 녹음. 체험학습 PDF가 즉시 출력 — 학교 양식 그대로.
> 5. **F5 RTO 대시보드** — 충남 CACF 화면 전환, 공주·부여 시군 무장애 정보 누락 5곳 히트맵 + 사용자 제보 빈도 상위 3 POI.
> 6. **마무리 메시지** — *"AI 기본법 2026년 1월 22일 시행. 우리는 그 의무를 출시일인 5월부터 이미 준수합니다. 무장애 여행이 자녀의 교육 산출물로 남는 첫 서비스입니다."*

### D.2 보조 시연 (질의응답 대비) — "외국인 + 야간관광"

| 맞춤형 API | 여러 기관 데이터를 특정 주제로 표준화해 제공 |
| 전국 다국어 가이드 제공 문화시설 | 영어, 중국어 등 다국어 가이드 제공 문화시설 데이터 |
| 전시정보(통합) | 여러 문화기관의 전시 정보를 공통 항목으로 표준화 |
| 전국 시티투어 코스와 함께하는 맛집 정보 | 전국시티투어정보표준데이터와 음식점 데이터를 결합한 맞춤형 API |

문화공공데이터광장은 TourAPI의 관광 POI를 직접 대체하기보다는 공연·전시·문화시설·문화행사·문화재 데이터를 결합할 때 필요한 보조 데이터원이다.

## 5. 문화빅데이터 플랫폼

URL: https://www.bigdata-culture.kr/

문화빅데이터 플랫폼은 한국문화정보원이 운영하는 문화·체육·관광 분야 데이터 유통/분석 플랫폼이다. 한국문화정보원 사업 안내 페이지는 문화빅데이터 플랫폼이 공공기관과 민간기업 협업으로 데이터를 생산·수집·가공·유통해 데이터 활용 생태계 조성에 기여한다고 설명한다.

플랫폼 메인과 사업 안내에서 확인되는 관련 분야:

| 분야 | 데이터 예 |
| --- | --- |
| 관광 | 관광지, 축제, 공연 등 문화 행사 정보, 지역별 관광명소, 지역 문화재, 관광 연관시설 |
| 음식 | 국내 식당 및 메뉴, 카페·디저트, 무슬림 친화식당 |
| 숙박 | 숙박·레저시설, 호텔 및 주변 편의시설 |

| 한류 | 방한객 문화향유 행태, 해외 한류 키워드 분석 |

개발 관점에서 문화빅데이터는 직접 API형 실시간 POI 검색보다는 리포트, 데이터 상품, 분석/시각화, 맞춤형 데이터 신청에 가까운 자료원이다. 데이터 라이선스와 유료/무료 여부가 상품별로 다를 수 있으므로 서비스에 편입하기 전 개별 상품 조건 확인이 필요하다.

## 1. 웹 접근성 — 한국형 웹 콘텐츠 접근성 지침 (KWCAG) 2.2

### 1.1 KWCAG 2.2 개요
- 정식 명칭: **한국형 웹 콘텐츠 접근성 지침 2.2** (Korean Web Content Accessibility Guidelines 2.2)
- 국가표준 (TTAK.OT-10.0003/R3 등 KS X 6308 계열)
- 1차 출처: https://a11ykr.github.io/kwcag22/
- 한국정보접근성인증평가원: https://www.wa.or.kr/m1/sub1.asp
- 한국디지털접근성진흥원: http://www.kwacc.or.kr/Accessibility/Certification

### 1.2 법적 기반
- **디지털포용법** 제21조 + 시행령 제20조
- **장애인차별금지 및 권리구제 등에 관한 법률** (장차법) 제20조, 제21조 — 정보접근권
- 1차 출처: http://www.kwacc.or.kr/Accessibility/Law

### 1.3 KWCAG 2.2 구조
- **4가지 원칙** (POUR: Perceivable, Operable, Understandable, Robust)
- **14개 지침** (각 원칙별 세부 지침)
- **33개 검사항목**

#### 4대 원칙

| 원칙 | 지침 수 | 핵심 내용 |
|------|---------|---------|
| **인식의 용이성 (Perceivable)** | 5 | 대체 텍스트, 멀티미디어 자막/대체수단, 명료성(색·명도 대비, 폰트), 명도 대비 비율 (4.5:1 이상) |
| **운용의 용이성 (Operable)** | 4 | 키보드 접근, 충분한 시간 제공, 광과민성 발작 방지, 쉬운 내비게이션 |
| **이해의 용이성 (Understandable)** | 3 | 가독성, 예측 가능성, 입력 도움 (오류 메시지, 레이블) |
| **견고성 (Robust)** | 2 | 문법 준수, 웹 애플리케이션 접근성 |

### 1.4 주요 검사항목 (33개 중 핵심)
- 1.1.1 적절한 대체 텍스트 (alt 속성)
- 1.2.1 자막 제공 (영상)
- 1.3.1 색 의존성 회피
- 1.3.2 명도 대비 (텍스트 4.5:1, 큰 텍스트 3:1)
- 2.1.1 키보드 사용 보장
- 2.2.1 응답 시간 조절 (충분한 시간)
- 2.2.2 정지 기능 제공 (자동 재생/이동)
- 2.3.1 깜빡임/번쩍임 (초당 3~50회 사이 금지)
- 2.4.1 반복 영역 건너뛰기 (스킵 내비게이션)
- 2.4.2 제목 제공 (페이지·프레임·콘텐츠)
- 3.1.1 기본 언어 표시 (lang 속성)
- 3.2.1 사용자 요구에 따른 실행
- 3.3.1 콘텐츠 선형 구조 + 표 마크업
- 3.3.2 레이블 제공 (입력 양식)
- 4.1.1 마크업 오류 방지
- 4.1.2 웹 애플리케이션 접근성 (WAI-ARIA)

### 1.5 적용 대상
- PC 웹, 터치스크린 기기, **모바일 기기 모든 웹 콘텐츠**
- 반응형 웹은 KWCAG 2.2 단일 적용 가능

## 2. 모바일 앱 접근성 — 한국형 모바일 애플리케이션 콘텐츠 접근성 지침

### 2.1 표준
- 정식 명칭: **모바일 애플리케이션 콘텐츠 접근성 지침 2.0** (KS X 3253)
- 인증 절차: 한국정보접근성인증평가원, 한국디지털접근성진흥원 등 국가공인 평가기관
- 1차 출처: http://www.kwacc.or.kr/Accessibility/Certification

### 2.2 모바일 앱 접근성 핵심 원칙
- 인식의 용이성: 대체 텍스트, 색 의존성 회피, 명도 대비
- 운용의 용이성: **터치 제스처 대안 제공**, 초점, 응답 시간 조절
- 이해의 용이성: 텍스트 콘텐츠의 명확성, 사용자 인터페이스 일관성, 알림 기능
- 견고성: 접근성 속성, 보조기술 호환성

### 2.3 OS별 접근성 가이드
- **iOS**: VoiceOver, Dynamic Type, Smart Invert, Switch Control 등 — Apple Human Interface Guidelines (Accessibility)
- **Android**: TalkBack, Live Caption, Switch Access 등 — Android Accessibility Guidelines

### 2.4 인증 마크
- 정보통신접근성(웹·앱) 품질 마크
- 유효기간: **1년** (재인증 필요)
- 인증기관: 한국디지털접근성진흥원, 한국정보접근성인증평가원, 웹와치 등

## 3. WAI-ARIA (Accessible Rich Internet Applications)

### 3.1 ARIA 개요
- W3C 표준 — 동적 콘텐츠와 사용자 인터페이스 컴포넌트의 접근성 향상
- KWCAG 2.2 검사항목 4.1.2 (웹 애플리케이션 접근성)에서 ARIA 적용 권장

### 3.2 핵심 ARIA 속성
- `role` (button, dialog, navigation, alert, status 등)
- `aria-label`, `aria-labelledby`, `aria-describedby` (접근 가능한 이름)
- `aria-expanded`, `aria-hidden`, `aria-current` (상태)
- `aria-live` (실시간 업데이트 알림)
- `aria-controls`, `aria-haspopup` (관계)

### 3.3 SPA/React/Vue/Next.js 등 적용
- 시맨틱 HTML 우선, ARIA는 보조
- 페이지 라우팅 시 포커스 관리 (스크린 리더 사용자 안내)
- 모달/드로어/탭 컴포넌트 ARIA role 명시

## 4. AI 기본법 (인공지능 발전과 신뢰 기반 조성 등에 관한 기본법)

### 4.1 법령 개요
- 정식 명칭: **인공지능 발전과 신뢰 기반 조성 등에 관한 기본법** (약칭: AI 기본법)
- 제정·공포: **2025. 1. 21.**
- **시행: 2026. 1. 22.** (디지털의료기기 관련 조항은 2026. 1. 24.)
- 소관 부처: 과학기술정보통신부
- 1차 출처: https://www.law.go.kr/lsInfoP.do?lsiSeq=268543

### 4.2 적용 대상
- 한국 내에서 AI 시스템을 개발·제공·이용하는 자
- **국외 사업자도 한국 내 영향이 있으면 적용** (역외 적용 + 국내 대리인 지정 의무)

### 4.3 핵심 의무 (5가지)

| 의무 | 내용 | 적용 대상 |
|------|------|----------|
| **투명성 확보** | AI가 생성한 결과물임을 사용자에게 고지 (생성형 AI), 워터마크 등 | 모든 AI 사업자 |
| **안전성 확보** | 위험 평가, 안전 조치, 사고 대응 체계 | 모든 AI 사업자 |
| **고영향 AI 사업자 특별 책무** | 영향평가, 위험관리체계, 인적 감독, 문서화 | 고영향 AI (의료/금융/공공/교통/에너지/채용 등) |
| **AI 영향 평가** | 사회적 영향 사전 평가 | 고영향 AI |
| **국내 대리인 지정** | 해외 빅테크의 한국 내 대리인 지정 | 일정 규모 이상 외국 AI 사업자 |

### 4.4 생성형 AI 표시 의무 (제31조 등)
- 생성형 AI로 만든 결과물(텍스트/이미지/영상/음성)임을 **명확히 고지**
- 딥페이크 등 사실 오인 가능성 있는 콘텐츠 → **워터마크/메타데이터 표시 의무**

### 4.5 처벌
- 위반 시 과태료 (최대 3천만원)
- **계도 기간**: 시행 후 최소 1년 이상 (실제 과태료 부과는 2027년 이후로 예상)
- 통합 안내·지원 센터 운영 예정

### 4.6 출품작에서 생성형 AI 활용 시
- 챗봇·번역·이미지 생성 등 생성형 AI 활용 시 결과물에 "AI 생성" 표시
- 학습 데이터 출처 (KOGL 1유형 등) 명시
- 사용자 입력 데이터의 학습 활용 여부 처리방침 공개
- 편향·환각(hallucination) 가능성 사용자 고지

**3. 4 페르소나 검토**

P1 휠체어·시니어는 유지 가능하다. 다만 “시니어=휠체어”가 아니므로 피로도, 낙상 위험, 큰 글씨, 휴식 간격을 별도 요구로 써야 한다.

P2 시각·청각은 합치면 안 된다. 발표용 이름은 하나로 둬도, 요구사항은 P2a 시각, P2b 청각으로 분리해야 한다. 음성 안내와 자막/수어/시각 알림은 반대 성격의 UX다.

P3 유아차·자녀 가족은 F4의 주 타깃이므로 유지. P4 교사·복지기관은 일반 관광객이 아니라 구매자/운영자 성격이라 유지 가치가 있다.

외국인은 별도 페르소나로 다시 분리하는 편이 맞다. 다국어를 핵심 차별로 주장한다면 “언어 토글”만으로는 부족하다. P5 외국인 자유여행자 또는 외국인 가족을 부록/보조 시연에 추가하고, 1330·응급·교통·문화 맥락 니즈를 넣어야 한다. 4명 고정이면 외국인을 핵심 타깃이 아닌 횡단 모드로 낮춰 표현해야 한다.

**4. MVP 5기능 검토**

4개월 안에 “심사용 MVP”는 가능하지만 “운영 가능한 완성품”은 과장이다. 6 POI 한정, 수동 검수 데이터, 데모용 UGC를 전제로 해야 한다.

가장 위험한 기능은 F3 Waze UGC다. 사용자 풀이 없으면 24시간 3건 검증이 작동하지 않고, 잘못된 자동 재계산은 책임 문제가 생긴다. MVP에서는 “제보 접수 + 관리자 검수 큐 + 룰 기반 대체 경로”로 낮추는 게 안전하다.

F4 PDF는 PT 차별축으로 작동한다. 단, 그냥 사진·퀴즈 PDF면 흔하다. 국가유산청 해설, Odii 퀴즈, 방문 인증, 접근성 동선 기록, 교사용 요약을 묶어야 “무장애 헤리티지 체험학습”이 된다.

추가하면 좋은 1개는 음성 검색/명령이다. 챗봇보다 작고, 보호자 알림보다 규제 부담이 낮다. “휠체어로 갈 수 있는 공산성 코스 찾아줘”를 F1 진입점으로 넣으면 접근성과 PT 임팩트가 동시에 오른다.

**5. 채점 자기평가 비평**

현재 1차 92 + PT 91은 “상한 점수”다. 지금 문서 상태만 보면 1차 90~91, PT 89~90이 더 보수적이다. 외부 데이터와 범위 축소를 반영하면 92/91은 다시 방어 가능하다.

기획력 27/30은 적정하나 “한국 0” 주장은 근거 없으면 감점 포인트다. 완성도 26/30은 높다. F3를 베타로 낮추지 않으면 24~25가 맞다.

데이터 활용 19~20/20은 현재 19가 맞다. KTO 10개를 많이 쓰는 것보다 비KTO 데이터가 실제 기능에 들어가야 20이다. 위 TOP5를 F1/F4/F5에 넣으면 20 가능하다.

발전성 18/20은 적정, 충남 올담·BF·응급 데이터 환류 구조를 넣으면 19 가능하다. PT 적정성 27~28은 사회적 가치가 충분하지만 법·정책 나열보다 실제 사용자 장면이 더 중요하다. 발표 13~14/15는 핵심 시나리오 1개만으로는 13, 외국인/긴급 보조 시연까지 있으면 14다.

**6. 수정 권고**

1. “매뉴얼 정합성 100%” 표현은 검증표로 바꿔라. API별 `검증 완료/검증 중/운영 확인 필요` 상태를 붙이는 편이 더 안전하다.

2. 데이터 활용 섹션에 “KTO vs 비KTO 역할 분담표”를 추가하라. KTO는 관광 POI, 외부 데이터는 접근성 검증·교육·안전·RTO 근거로 분리한다.

3. F3는 MVP에서 자동 재계산을 낮춰라. “사용자 제보 → 관리자 검수 → 후속 사용자 경고 → 대체 경로 제안” 단계로 쓰는 게 방어 가능하다.

4. 외국인은 P5로 분리하거나 핵심 문구에서 낮춰라. “모두 접근 가능”을 말하려면 외국인 안전·상담·교통 니즈가 필요하다.

5. F4 PDF에 국가유산청 해설과 교사용 루브릭을 붙여라. 그래야 일반 PDF가 아니라 백제 헤리티지 교육 산출물이 된다.

**3. 4 페르소나 검토**

P1 휠체어·시니어는 유지 가능하다. 다만 “시니어=휠체어”가 아니므로 피로도, 낙상 위험, 큰 글씨, 휴식 간격을 별도 요구로 써야 한다.

P2 시각·청각은 합치면 안 된다. 발표용 이름은 하나로 둬도, 요구사항은 P2a 시각, P2b 청각으로 분리해야 한다. 음성 안내와 자막/수어/시각 알림은 반대 성격의 UX다.

P3 유아차·자녀 가족은 F4의 주 타깃이므로 유지. P4 교사·복지기관은 일반 관광객이 아니라 구매자/운영자 성격이라 유지 가치가 있다.

외국인은 별도 페르소나로 다시 분리하는 편이 맞다. 다국어를 핵심 차별로 주장한다면 “언어 토글”만으로는 부족하다. P5 외국인 자유여행자 또는 외국인 가족을 부록/보조 시연에 추가하고, 1330·응급·교통·문화 맥락 니즈를 넣어야 한다. 4명 고정이면 외국인을 핵심 타깃이 아닌 횡단 모드로 낮춰 표현해야 한다.

**4. MVP 5기능 검토**

4개월 안에 “심사용 MVP”는 가능하지만 “운영 가능한 완성품”은 과장이다. 6 POI 한정, 수동 검수 데이터, 데모용 UGC를 전제로 해야 한다.

가장 위험한 기능은 F3 Waze UGC다. 사용자 풀이 없으면 24시간 3건 검증이 작동하지 않고, 잘못된 자동 재계산은 책임 문제가 생긴다. MVP에서는 “제보 접수 + 관리자 검수 큐 + 룰 기반 대체 경로”로 낮추는 게 안전하다.

F4 PDF는 PT 차별축으로 작동한다. 단, 그냥 사진·퀴즈 PDF면 흔하다. 국가유산청 해설, Odii 퀴즈, 방문 인증, 접근성 동선 기록, 교사용 요약을 묶어야 “무장애 헤리티지 체험학습”이 된다.

추가하면 좋은 1개는 음성 검색/명령이다. 챗봇보다 작고, 보호자 알림보다 규제 부담이 낮다. “휠체어로 갈 수 있는 공산성 코스 찾아줘”를 F1 진입점으로 넣으면 접근성과 PT 임팩트가 동시에 오른다.

**5. 채점 자기평가 비평**

현재 1차 92 + PT 91은 “상한 점수”다. 지금 문서 상태만 보면 1차 90~91, PT 89~90이 더 보수적이다. 외부 데이터와 범위 축소를 반영하면 92/91은 다시 방어 가능하다.

**6. 수정 권고**

1. “매뉴얼 정합성 100%” 표현은 검증표로 바꿔라. API별 `검증 완료/검증 중/운영 확인 필요` 상태를 붙이는 편이 더 안전하다.

2. 데이터 활용 섹션에 “KTO vs 비KTO 역할 분담표”를 추가하라. KTO는 관광 POI, 외부 데이터는 접근성 검증·교육·안전·RTO 근거로 분리한다.

3. F3는 MVP에서 자동 재계산을 낮춰라. “사용자 제보 → 관리자 검수 → 후속 사용자 경고 → 대체 경로 제안” 단계로 쓰는 게 방어 가능하다.

4. 외국인은 P5로 분리하거나 핵심 문구에서 낮춰라. “모두 접근 가능”을 말하려면 외국인 안전·상담·교통 니즈가 필요하다.

5. F4 PDF에 국가유산청 해설과 교사용 루브릭을 붙여라. 그래야 일반 PDF가 아니라 백제 헤리티지 교육 산출물이 된다.

6. F1 진입점에 음성 검색을 추가하라. 접근성 시연, P1/P2 설득, PT 첫 장면을 동시에 강화한다.
