# 00 — 기획안 (읽는 법과 경계)

> **이 폴더는 두 번째 기능명세가 아니다.**
> 「모두의 백제」를 **무엇을 만드는가**로 설명하는 곳은 [`docs/spec/`](../spec/00_README.md)이고, 이 폴더는 그 앞뒤 두 층만 다룬다 — **왜 이 제품이 필요한가**(spec보다 앞)와 **만든 뒤에 무엇이 남는가**(spec보다 뒤).
> 구현 범위·수치·동작이 이 폴더와 spec에서 어긋나면 **언제나 spec이 이긴다.** 이 폴더의 문장을 지우고 spec 링크로 바꾼다.

---

## 1. 왜 이 규칙을 맨 앞에 두는가

`docs/plan/`에는 2026년 6월에 쓴 기획 문서 19개가 있었다. 2026-09-01에 전부 삭제됐다.

삭제 이유는 두 가지인데, 두 번째가 더 중요하다.

1. 개발 기간과 인원 전제가 무너졌다 ([`spec/00_README.md`](../spec/00_README.md) §1·§2).
2. **그 문서들이 아키텍처·데이터 모델·기능 명세·접근성·법무·테스트를 spec과 나란히 두 번 썼고, 두 사본의 수치가 서로 갈라지기 시작했다.**

두 번째는 기간이 다시 늘어나도 재발한다. 사본이 둘이면 갈라지고, 갈라진 뒤에는 어느 쪽이 맞는지 아무도 모른다. 그래서 이 폴더는 **소유하지 않는 것을 먼저 적고 시작한다.**

## 3. 편집 규칙

### 3.1 숫자를 옮겨 적지 않는다

아래는 전부 spec 소유다. 이 폴더는 링크로 대신한다.

가중치 · 상태값 · 임계값 · 항목 개수 · 화면 개수 · API 종수 · 호출 예산 · 테스트 건수 · 배점 · 일정 · 마이그레이션 수 · 캐시 주기 · 리전 · 버전 · 법령 조문 번호.

> 예: "가중치는 [`spec/06_suitability.md`](../spec/06_suitability.md) §3" 이라고 쓴다. `0.30`이라고 쓰지 않는다.

**유일한 예외**는 이 폴더가 **스스로 계산하거나 관측한 값**이다. 그때는 (a) 계산 근거를 함께 적고 (b) 입력이 spec의 어느 절에서 왔는지 링크한다. [`02_claims_and_validation.md`](./02_claims_and_validation.md) §3의 산식 검산이 그 경우다.

그 밖의 문장은 **숫자가 바뀌어도 살아남게** 쓴다. "17건이 비어 있다"가 아니라 "절반 이상이 비어 있다".

### 3.2 링크는 한 방향으로만 흐른다

기획안 → spec만 링크한다. **spec은 기획안을 링크하지 않는다.**

> **지금 상태는 그렇지 않다 — 알려진 예외 하나가 있다.**
> [`spec/13_legal_citations.md`](../spec/13_legal_citations.md) 서문이 **삭제된** `docs/plan/11_legal_compliance.md`·`10_accessibility_kwcag.md`를 내용의 원 출처로 적고 있다. 링크가 아니라 산문이고 대상이 이미 없으므로 당장 깨지는 것은 없지만, **§3.5 검사 (2)는 이걸 매번 잡는다.** 그게 맞다 — 새 위반과 구분되지 않는 채로 조용히 통과시키는 것보다 낫다.
> 정리하려면 spec/13을 고쳐야 하는데 이 폴더는 spec을 고칠 수 없다. [`02_claims_and_validation.md`](./02_claims_and_validation.md) §5.1에 올려 뒀다.

이유: spec은 계속 움직인다. spec이 기획안을 참조하기 시작하면 spec을 고칠 때마다 기획안을 함께 고쳐야 하고, 그 순간 두 문서가 한 몸이 되어 "어느 쪽이 이기는가"가 무의미해진다.

### 3.3 삭제 시험

문단을 하나 쓸 때마다 묻는다.

> **`docs/plan/`을 통째로 지우면 `docs/spec/`이 그대로 서는가?**

답이 "아니오"면 그 문단은 spec으로 가야 할 내용을 여기 쓴 것이다. 옮기거나 지운다.
반대 방향("spec을 지우면 기획안이 무너진다")은 정상이다. 기획안은 spec 위에 서 있다.

### 3.4 새 문서를 만들려면 관문을 통과한다

새 기획안 문서를 추가하려면, **그것이 답하는 질문을 spec 14개 문서 중 어느 것도 답하지 않는다는 것을 파일명과 절 번호로 보여야 한다.** 통과하지 못하면 그것은 새 문서가 아니라 사본이다.

### 3.5 위 규칙을 실제로 확인하는 방법

**§7 마지막 줄이 "규칙은 오늘 데이터에서 빨간불이 될 수 있어야 한다"고 정했다. 그러려면 검사하는 방법이 적혀 있어야 한다.**

아래 넷은 자동화가 아니라 **손으로 붙여넣어 돌리는 명령**이다. CI에 걸지 않는다 — §7이 금지했고 그 판단은 그대로다. 이 폴더를 고칠 때, 그리고 spec을 크게 고친 뒤에 한 번씩 돌린다.

> **셋 다 리포지토리 루트에서 실행한다. 어느 명령도 작업 디렉터리를 바꾸지 않는다.**
> (앞 판의 검사 (3)은 `cd docs/plan`으로 시작해 되돌아오지 않았다. 순서대로 돌리면 그다음 검사가 없는 경로를 훑고 **빈 출력 = 통과**로 읽힌다. 이 세션에서 실제로 같은 사고가 났다.)

**검사 대상은 `README.md` + `docs/plan/0*.md`다.** 루트 README도 이 규칙을 지켜야 한다 — 진입점이 spec과 다른 숫자를 말하면 가장 먼저 읽는 사람이 가장 먼저 속는다.

**(1a) 개수·값을 옮겨 적었는가** — spec 링크가 같은 줄에 있어도 면제되지 않는다

```bash
for F in README.md docs/plan/0*.md; do
  awk -v F="$F" '/^```/{f=!f;next} !f{print F":"NR": "$0}' "$F"
done | grep -E '[0-9]+곳|[0-9]+개 항목|원칙 [0-9]+개|[0-9]+가지 원칙|[0-9]+종|[0-9]+채널|[0-9]+점|0\.[0-9]{2}' \
     | grep -v '<!--검산-->' | grep -v '라고 쓰지 않는다'
```

**개수는 링크를 붙여도 사본이다.** "spec의 원칙 7개"라고 쓰면 spec이 6이라고 고쳤을 때 두 문서가 갈라진다 — 링크가 있다고 막아지지 않는다. 코드 펜스 안(§3.1이 허용한 자체 계산)과 `<!--검산-->` 표시가 붙은 줄만 제외된다.

> **이 검사는 실제로 빨간불이 났다.** 이 폴더를 쓰는 동안 두 번 — 처음 돌렸을 때 `6곳` 네 곳과 링크 없는 `1주차`, 그리고 규칙을 고친 뒤 다시 돌렸을 때 루트 README의 `원칙 7개`(연결된 spec 제목은 다른 수를 쓴다). 전부 고쳤다. <!--검산-->
>
> 같은 회차에 손으로 잡은 `다섯 페르소나`와 `약 4주`는 **이 정규식이 잡지 못한다** — 숫자가 한글이거나 `주차` 형태가 아니다. 검사가 덮는 범위를 넘겨 말하지 않는다.

**(1b) 일정을 옮겨 적었는가** — 이쪽은 spec 링크가 있으면 위반이 아니다

```bash
for F in README.md docs/plan/0*.md; do
  awk -v F="$F" '/^```/{f=!f;next} !f{print F":"NR": "$0}' "$F"
done | grep -E '[0-9]+주차|Day [0-9]' | grep -v '/spec/' | grep -v '<!--검산-->'
```

`1주차`는 값이 아니라 **가리키는 자리**다. 링크가 함께 있으면 "저기를 보라"는 뜻이므로 통과시킨다. <!--검산-->

**(2) spec이 기획안을 역참조하기 시작했는가**

```bash
grep -rnE '(docs/plan|\.\./plan)/[0-9]{2}_' docs/spec/
```

**두 자리 전부를 본다** — 앞 판은 `0[0-3]_`만 봐서 `10_`·`11_`을 놓쳤고, §3.4가 허용한 다섯 번째 문서도 못 잡았을 것이다.
지금 이 검사는 **한 건을 잡는다**(§3.2의 알려진 예외). 그 한 줄이 사라지기 전까지는 "출력이 그 한 줄뿐인가"가 통과 조건이다.

**(3) 링크가 살아 있는가**

```bash
for F in README.md docs/plan/0*.md; do
  d=$(dirname "$F")
  grep -ohE '\]\(\.{1,2}/[A-Za-z0-9_./-]+\.(md|txt)\)' "$F" | sed 's/](//;s/)$//' | while read -r p; do
    [ -e "$d/$p" ] || echo "DEAD $F -> $p"
  done
done | sort -u
```

**대문자를 포함하는 파일명을 반드시 넣는다.** 앞 판의 문자 클래스가 소문자뿐이라 **`00_README.md`를 가리키는 링크 14개가 전부 검사에서 빠져 있었다** — 이 폴더에서 가장 많이 인용하는 파일이 유일하게 검사되지 않는 상태였다. 지금은 206개를 본다.

> **이 검사가 없어서 실제로 사고가 났다.** [`_research/`](./_research/) 안의 리뷰 문서들이 `docs/plan/NN_*.md:줄번호` 형식으로 인용하고 있었는데, 가리키던 파일들이 삭제되면서 **인용이 전부 죽었고 아무도 몰랐다.**

**절 번호까지는 자동으로 못 본다.** spec의 제목 형식이 파일마다 다르고(`## S1 —`, `## Day 1~2`, `## 3b.`), 이 폴더가 인용하는 것 대부분이 `###` 하위 절이라 한 줄짜리 grep으로는 덮이지 않는다. **인용한 절 번호는 링크를 눌러 눈으로 확인한다.** 자동화할 수 있는 척하지 않는다. <!--검산-->

**§3.3(삭제 시험)과 §3.4(새 문서 관문)에도 명령이 없다.** 둘 다 판단이다.

|---|---|
| **[확인]** | 원문·실호출·직접 계산으로 확인했다. 출처를 함께 적는다 |
| **[설계확정]** | **우리가 그렇게 만들기로 정했다.** 확인한 것이 아니다 — 코드가 0줄인 동안 구현 관련 주장은 전부 이 상태다. 만들어져서 시연으로 보인 뒤에 `[확인]`으로 올린다 |
| **[미확인]** | 아직 확인하지 못했다. **이 상태로 발표에서 단언하지 않는다** |
| **[확인예정]** | 확인 방법과 시점이 정해져 있다. [`spec/11_open_items.md`](../spec/11_open_items.md)의 항목 번호를 붙인다 |
| **[가설]** | 검증 계획이 있는 제품 가설. 반증 조건을 함께 적는다 |
| **[반증]** | 확인해 봤더니 틀렸다. **틀렸다는 사실과 그 뒤에 무엇을 할지를 남긴다** |
| **[유도반증]** | spec의 값으로 **직접 계산해 보니 spec의 선언과 어긋나는 출력이 나왔다.** 관측이 아니라 파생이므로 `[반증]`보다 약하다 — 실데이터가 다르게 나올 여지가 남아 있고, 그 조건을 함께 적는다 |
| **[부분 확인]** · **[부분 반증]** | 주장의 일부만 참이거나 일부만 무너졌다. **어느 부분인지 반드시 함께 적는다** |
| **[미결 PD-N]** | 이 폴더가 발견했지만 **spec을 고쳐야 풀리는 결정.** 접두사가 `PD-`인 이유는 `spec/11_open_items.md` §2가 `DEC-`/`D-`/`O-`/`P0-` 넷을 이미 쓰고 있어서다. **채택되면 `spec/11`의 `DEC-`로 옮기고 여기서 지운다** — 결정 번호가 두 곳에 살면 안 된다 |

## 6. `_research/`를 남겨 둔 이유와 주의

[`_research/`](./_research/)에는 2026년 6월의 1차 조사(D1~D4 · R1~R5)와 당시 리뷰 findings가 남아 있다. **조사 원본이라 대체할 수 없어서 남겼다.**

두 가지를 주의한다.

1. **권위가 없다.** 그 문서들은 Next 15 · Node 20 · PostGIS · 병렬 에이전트 팀 · 3.5개월을 전제로 쓰였다. 같은 주제에서 spec과 어긋나면 **spec이 맞다.** 특히 한국관광공사 API 사실은 [`spec/03_external_data.md`](../spec/03_external_data.md)가 매뉴얼 원문 대조로 다시 확정했다.
2. **그 안의 `docs/plan/NN_*.md:줄번호` 인용은 더는 유효하지 않다.** 가리키던 파일이 삭제됐다. 필요하면 `git log -- docs/plan/`으로 커밋을 찾아 `git show <커밋>:docs/plan/...`으로 본다. 리뷰 문서 자체는 그 시점의 기록이므로 고치지 않는다.

## 7. 하지 않는 것

| 안 하는 것 | 이유 |
|---|---|
| spec 파일과 1:1로 대응하는 문서 (아키텍처 · 데이터 모델 · 기능 명세 · 테스트 · 일정 · 법무 · 산식 정책) | 삭제된 19개 중 일곱이 정확히 이거였다 |
| 발표 대본 · 슬라이드 구성 · 예상 질문 | [`spec/12_judging_and_demo.md`](../spec/12_judging_and_demo.md) §4·§6 소유 |
| 제안서 문장 교체표 | [`spec/_proposal-delta.md`](../spec/_proposal-delta.md) 소유. 제출본은 애초에 고칠 수 없다 |
| 화면 목업 · 와이어프레임 | [`spec/07_screens.md`](../spec/07_screens.md)가 갖고 있다. 두 벌이 되면 갈라진다 |
| 추정 점수 · 자체 채점 | [`spec/12_judging_and_demo.md`](../spec/12_judging_and_demo.md) §7이 금지했고, 여기서 되살리면 같은 실수의 재발이다 |
| 새 용어 · 새 페르소나 | spec이 정한 말만 쓴다. 새로 지으면 화면·발표·문서가 세 갈래로 갈린다 |
| 한/영 mirror 문서 | 같은 내용 두 사본이 다시 갈라진다 |
| 문서 정합 CI · 버전 잠금 · 문서 해시 · CODEOWNERS | 저자가 1명이다. 그리고 지금까지 발견된 충돌은 대부분 **의미 충돌**이라 자동 동일성 검사로 잡히지 않는다. [`spec/00_README.md`](../spec/00_README.md) 원칙 6이 이미 금지했다 |

마지막 행에 하나 덧붙인다. **규칙을 만들려면 그 규칙이 오늘 데이터에서 실제로 빨간불이 될 수 있어야 한다.** 될 수 없으면 만들지 않는다. 켜 두고 통과만 하는 검사는 없는 것보다 나쁘다 — 세어지고, 신뢰받고, 조용하기 때문이다.
