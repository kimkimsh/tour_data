## 1. 왜 이 문서가 필요한가

이 제품은 **근거를 무기로 삼는다.** 판정의 근거를 전부 공개하고, 못 한 것을 못 했다고 쓰고, 매뉴얼 원문 대조로 사실을 바로잡았다는 것이 주장의 골자다.

**근거를 무기로 삼는 제품에서 틀린 근거 하나는 강점을 약점으로 바꾼다.** 게다가 공모전 공고문에는 **허위 기재 시 평가대상 제외·수상 취소** 조항이 있고([`spec/12_judging_and_demo.md`](../spec/12_judging_and_demo.md) §1), 1차 심사는 "서면 **및** 기능심사"라 제출된 제안서가 완성 서비스와 나란히 다시 채점된다.

그래서 이 문서는 **주장마다 상태를 붙인다.** 상태 표기는 [`00_README.md`](./00_README.md) §5.

**읽는 시점: 발표·제출 직전마다.** [미확인]이 남아 있는 행을 그 자리에서 확인하거나, 확인 못 하면 그 행의 "물러설 문장"으로 바꿔 말한다.

## 3. ★★★ 주장 4의 반증 — 산식이 원칙 1을 뒤집었다 (해소됨)

> **★ 이 절은 기록으로 남는다. 문제는 2026-09-01에 고쳐졌다.**
> `0~49` 구간이 `주의`로 바뀌고 `대체추천`은 **확인된 `unsupported`** 로만 도달한다. `alternatives`도 점수 비교에서 **라벨 비교**로 바뀌어 "다른 곳 권장 → 대신 여기도 다른 곳 권장"이 사라졌다.
> 결정 기록은 [`spec/11_open_items.md`](../spec/11_open_items.md) **DEC-7**, 산식은 [`spec/06_suitability.md`](../spec/06_suitability.md) §6.4 하위 절이 갖는다. **아래 §3.1의 계산은 그 결정의 근거이므로 지우지 않는다** — 같은 실수가 다시 들어오면 이 반례가 다시 잡는다.
> **§3.5의 미결 PD-1은 닫혔다.** 처방 A·B는 채택되지 않았고, 더 작은 세 번째 수정으로 갔다 (§5.1 ★1).

**이 절이 이 문서에서 가장 중요하다.** 그리고 이 폴더가 spec의 수치를 다시 쓰지 않는다는 규칙([`00_README.md`](./00_README.md) §3.1)의 유일한 예외다 — **아래는 spec의 수치를 옮긴 것이 아니라 그 수치로 우리가 직접 계산한 결과**이기 때문이다.

| **확인일** | **한국관광공사 항목 여섯 개는 91~365일 전, 파생 항목 셋은 90일 이내** | ← **이게 숨은 가정이었다.** 아래 주 참조 |

> **확인일 가정을 바꾸면 어떻게 되나.** 전부 90일 이내면 신선도 계수가 최대가 되어 점수가 **약 48**로 오른다.
> **그래도 라벨은 바뀌지 않는다** — 48도 `0~49` 구간이다. **반례에 가장 유리한 가정을 넣어도 결론이 살아남는다.**
>
> **★ DEC-9으로 신선도가 식에서 빠진 뒤에는 이 관광지의 점수가 `100 × 0.5339 × 0.9045 = 48`로 확정된다.** 확인일 가정 자체가 사라졌다. **48은 여전히 옛 규칙의 최하 구간이므로 반례는 그대로 성립하고**, 지금 규칙(DEC-7)에서는 `주의 · 확인 필요: 엘리베이터`가 된다. <!--검산-->

**조건: 휠체어 이용(P1a).**

```
축별 원점수 (축 안은 단순 평균)
  진입     (1 + 1 + 1 + .35 + .35 + .35) / 6   = 0.6750
  이동     (1 + .35 + .35 + .35) / 4           = 0.5125
  편의시설 (1 + 1 + .35×5) / 7                 = 0.5357
  정보안내  전 항목 unknown                     = 0.3500
  휴식      전 항목 unknown                     = 0.3500
  상황     (.5 + .35 + 1 + .5) / 4             = 0.5875

A = .30(.6750) + .18(.5125) + .18(.5357) + .14(.3500) + .10(.3500) + .10(.5875)
  = 0.5339

B = 0.75 + 0.25 × (34.0 / 55)   ← P1a 등급 가중치 합 55, 가중 점수 합 34.0
  = 0.9045

C = 1.00                         ← 인증 없음
D = (6 × 0.90 + 3 × 1.00) / 9    ← status ≠ unknown 인 9개 항목만
  = 0.9333

score = 100 × 0.5339 × 0.9045 × 1.00 × 0.9333 = 45
```

**라벨 결정** ([`spec/06`](../spec/06_suitability.md) §6.4 순서대로):

| 규칙 | 발동? | 이유 |
|---|---|---|
| 1) 필수 중 `unsupported`가 있으면 → 대체추천 | ✗ | `unsupported`가 하나도 없다. 모르는 것뿐이다 |
| 2) 필수 중 `unknown`이 과반이면 → 정보없음 | ✗ | 필수 다섯 개 중 하나만 모른다 |
| 3) 점수 구간 | **발동** | 45점 → 최하 구간 <!--검산--> |
| 4) 라벨 상한 | 무관 | 상한은 위로 못 올라가게 막을 뿐, 아래에서 끌어올리지 않는다 |

### 3.2 결과

> **접근로 · 출입통로 · 휠체어 · 장애인 화장실이 전부 "확인됨"인 관광지에 대해, 이 서비스는 휠체어 사용자에게 「다른 곳 권장」이라고 말한다.**

**[`spec/00_README.md`](../spec/00_README.md) §4 원칙 1이 "빈 값은 불가가 아니다"라고 선언하고, 산식이 그 선언을 정확히 뒤집는다.** 화면에서 보면 "모르는 것을 불가로 추론한 결과"와 구별되지 않는다.

**그리고 대체할 곳이 없다.** 점수가 낮으면 더 높은 곳을 제시하는데([`spec/06`](../spec/06_suitability.md) §6.5), 대상 관광지가 전부 같은 데이터 상태이므로 실제 화면은 **"다른 곳 권장 → 대신 여기는 어떠세요: 다른 곳 권장"**이 된다.

### 3.3 이건 임계값 조정으로 못 푼다

[`spec/06`](../spec/06_suitability.md) §6.4 하위 절이 이 상황을 예상하고 "1주차에 실데이터로 구간 임계값을 한 번 조정한다"고 대비해 뒀다. **그걸로 부족한 이유가 둘이다.**

**첫째, 대상 관광지가 모두 좁은 구간에 몰리면 임계값을 어디에 놓아도 라벨이 관광지 하나의 데이터 갱신에 뒤집힌다.** 그리고 점수의 의미가 절대 판정에서 **"대상 관광지 안에서의 상대 순위"**로 조용히 바뀐다. 상대 순위를 절대 판정처럼 표시하는 것은 원칙 5(못 한 것은 못 했다고 쓴다)에 걸린다.

**둘째 — 이게 더 근본적이다.** 항목 대부분이 상수(`unknown` 값)면, 점수 차이의 대부분이 **"어느 칸이 찼는가"가 아니라 "몇 칸이 찼는가"**에서 나온다. 그러면 적합도 점수는 **채움률의 다른 표기**이고, 갭 리포트가 이미 채움률을 직접, 더 정직하게 보여준다. **두 화면이 같은 것을 두 번 말하게 된다.**

또 하나: [`spec/07`](../spec/07_screens.md) S2의 완료 기준은 "조건을 바꾸면 순서와 라벨이 실제로 바뀐다"이고 E2E가 이를 검증한다([`spec/09`](../spec/09_test_and_ci.md) §5.1 16번). **실데이터에서 이 테스트는 "전부 정보없음"이라는 형태로도 통과한다** — 라벨은 바뀌지만 모든 관광지가 같은 값이라 순서에 의미가 없다. 통과하지만 아무것도 증명하지 못하는 검사다.

### 3.4 무엇이 쓸모 있고 무엇이 쓸모없는지 나눠서 본다

**채움률이 낮을수록 오히려 값이 올라가는 것 — 전부 유지한다.**

- 무장애 항목의 원문 문장·원래 필드명·확인일 노출
- 모르는 필수 항목의 **이름**을 알려주는 것 ("확인 필요: 엘리베이터")
- 본질 제약 / 운영자 미입력 구분
- 갭 리포트
- 경로 단계 카드, 항상 보이는 도슨트 대본

**실데이터에서 변별력이 사라지거나 사실과 반대되는 것.**

- 점수 숫자
- 4단계 라벨의 변별
- 대체 관광지 추천

### 3.5 처방 — 검토했고 **셋 중 어느 것도 아닌 더 작은 수정**으로 갔다 (PD-1 닫힘)

> **★ 2026-09-01 결정: 처방 A도 B도 아니다.** 아래 두 처방은 각각 부족하거나 컸고, 실제 채택된 것은 **라벨 규칙 한 줄**이다 — `0~49` 구간을 `주의`로 바꾸고 `대체추천`을 규칙 1 전용으로 두는 것. 처방 B가 지적한 근거 1·3·4가 그 한 줄로 충족되고, **근거 2(신선도가 점수를 깎는다)는 [`spec/11`](../spec/11_open_items.md) `DEC-9`가 별도로 처리했다 — 신선도를 점수 식에서 빼는 것으로.** 결과적으로 처방 B의 근거 넷이 전부 반영됐고, 반영 방법이 처방 B가 제안한 재작성보다 작았다.
> **아래 두 처방의 서술은 지우지 않는다** — 왜 더 큰 수정을 하지 않았는지의 기록이다.

> **기획안이 혼자 정할 수 없다.** [`spec/06`](../spec/06_suitability.md)과 [`spec/07`](../spec/07_screens.md)을 고치는 일이고, 고칠지 말지는 사람의 결정이다. **채택되면 이 절을 지우고 [`spec/11_open_items.md`](../spec/11_open_items.md)의 `DEC-`로 옮긴다** — 결정 번호가 두 곳에 살면 안 된다.

#### 처방 A — 점수를 화면 아래로 내린다 (처음 낸 안)

카드 1급 요소를 "확인 n · 모름 n · 불가 n + 확인 필요 항목명"으로 바꾸고, 점수와 A·B·C·D는 계산 내역 절 안으로 내린다.

**이건 충분하지 않다.** 점수를 접힌 곳으로 옮겨도 **그 점수가 정렬·라벨·대체 관광지를 계속 지배한다** — [`spec/07`](../spec/07_screens.md) S2는 라벨 다음 점수순으로 정렬하고, [`spec/06`](../spec/06_suitability.md) §6.5는 점수가 기준 아래일 때 대체 관광지를 채운다. 화면에서 숫자만 감추면 §3.2의 "다른 곳 권장 → 대신 여기도 다른 곳 권장"은 그대로 남는다.

#### 처방 B — 점수가 판정을 지배하지 않게 한다 (권장)

**점수는 남기되, 라벨·정렬·대체 관광지를 점수에서 떼어 선택 조건의 필수 항목만으로 정한다.**

```
지금:   점수 → 라벨 → 정렬 → 대체 관광지        (unknown 값과 신선도가 전부에 곱해진다)

바꾸면: 필수 항목 상태 → 세 갈래 판정 → 정렬
        ├ 확인된 장벽 있음   → "이 조건에서는 어렵습니다" + 어느 항목인지
        ├ 확인 필요 있음     → "확인이 필요합니다: {항목명}"
        └ 전부 확인·지원됨   → "확인된 범위에서 이용 가능합니다"

        점수 · A/B/C/D · 신뢰도  →  계산 내역 절 안에만 (근거로 남는다)
```

**§3.1의 예시 관광지가 이 규칙에서 무엇이 되나:** 확인된 장벽 0 · 확인 필요 1(엘리베이터) · 확인·지원 4 → **"확인이 필요합니다: 엘리베이터"**. 「다른 곳 권장」이 나오지 않는다.

**근거 넷:**

1. **원칙 1이 산식에 반영된다.** `unknown`이 점수를 깎는 경로가 판정에서 사라진다. 모르는 것은 "모른다"로만 나온다.
2. **불확실과 부적합이 분리된다.** [`spec/06`](../spec/06_suitability.md) §6.3이 이미 *"데이터가 오래되거나 비어 있는 것은 불확실이지 부적합이 아니다"*라고 선언했는데, 신선도가 점수에 곱해지면서 그 선언이 지켜지지 않고 있었다. **이 변경이 spec의 자기 선언을 실제로 이행한다.**
3. **조건을 바꾸면 결과가 진짜로 바뀐다.** 필수 항목 집합이 조건마다 다르므로 [`spec/07`](../spec/07_screens.md) S2의 완료 기준과 [`spec/09`](../spec/09_test_and_ci.md) §5.1 16번 테스트가 의미를 갖는다.
4. **미결 하나가 통째로 사라진다.** 구간 임계값 조정([`spec/11`](../spec/11_open_items.md) O-6)이 필요 없어진다. 조정할 구간이 없다.

**이 처방이 무엇을 나쁘게 만드나 — 두 가지, 둘 다 실재한다.**

- **[`spec/06`](../spec/06_suitability.md) 재작성 범위가 크다.** 라벨 규칙 · 대체 관광지 규칙 · 골든 테스트가 전부 대상이고, [`spec/07`](../spec/07_screens.md) S2 정렬도 바뀐다. **착수 첫 주에 해야 하는 일이 늘어난다.**
- **`partial`(일부 가능)을 세 갈래 중 어디에 넣을지 정해야 한다.** 지금은 정해져 있지 않다. 「확인 필요」로 넣는 것이 안전하지만, 그러면 [`spec/09`](../spec/09_test_and_ci.md) §2의 골든 20번(*"필수가 `partial`이면 차단 규칙이 발동하지 않는다"*)이 지키던 경계가 다른 곳으로 옮겨간다.

**이 처방이 뒤집히는 조건:** P0-1 결과 대상 관광지의 채움률이 충분히 높고 서로 달라서 점수가 실제로 변별된다면, 지금 설계 그대로가 맞다. **착수 첫 주에 실데이터로 확인할 수 있다**([`spec/10`](../spec/10_build_order.md) 1주차). **그 확인 전에는 spec을 고치지 않는다** — 이 절의 반례는 가상 입력 하나이고, 실데이터가 다르게 나올 여지가 남아 있다.

## 4. 제안서가 약속한 것 — 어느 사실이 위험하고 무엇을 결정했나

문장별 대조는 [`spec/_proposal-delta.md`](../spec/_proposal-delta.md)가, 질문받았을 때의 답은 [`spec/12_judging_and_demo.md`](../spec/12_judging_and_demo.md) §6이 갖는다.

> **경계를 다시 긋는다.** [`00_README.md`](./00_README.md) §7이 "발표 대본·예상 질문"을 만들지 않기로 정했는데, **앞 판의 이 절은 답변 문장을 그대로 적고 있었다 — 자기 규칙 위반이었다.**
>
> 이 절이 갖는 것은 **① 어느 사실이 왜 위험한가 ② 그래서 무엇을 하지 않기로 결정했나** 둘뿐이다. 그 결정 위에서 실제로 뭐라고 말할지는 `spec/12` §6이 정한다.

### 4.1 위치정보법 — 순서를 거꾸로 말하면 미이행이 된다

제출 제안서는 **"위치기반서비스 신고를 운영 전에 마친다"**고 약속했다. 구현은 정반대로 갔다 — GPS를 아예 쓰지 않아 **신고 대상 자체가 아니게** 만들었다.

**위험:** 같은 사실을 **미이행 → 사후 설명** 순으로 놓으면 약속을 못 지킨 것으로 읽히고, **설계 변경 → 결과 → 증명** 순으로 놓으면 의도된 결정으로 읽힌다. 사실은 하나인데 순서가 결과를 바꾼다.

**결정 두 가지:**

1. **이 항목은 "축소"가 아니라 "설계 변경"으로 분류한다.** 근거 문서는 [`spec/13`](../spec/13_legal_citations.md) §1이고, 증명은 자동 시험이다([`spec/09`](../spec/09_test_and_ci.md) §5.1 15번).
2. **"면제"라는 낱말을 쓰지 않는다.** 면제는 우리가 위치기반서비스사업자임을 인정하는 말이다. **"해당하지 않는다"**가 정확하다 — 이건 표현 취향이 아니라 법적 지위의 문제다([`spec/13`](../spec/13_legal_citations.md) §1이 같은 구분을 한다).

말하는 문장 자체는 [`spec/12`](../spec/12_judging_and_demo.md) §6 소유다.

### 4.2 ★★ 충남 기관 데이터 플랫폼 — 특별상을 그 기관이 직접 심사한다

**이게 이 문서에서 두 번째로 위험한 항목이다.**

제출 제안서가 충남 선택 이유의 하나로 특정 기관의 데이터 플랫폼과의 결합을 들었다. **두 가지가 동시에 틀렸다.**

1. **협약이 없다.**
2. **귀속이 틀렸다.** 그 플랫폼 중 하나는 도 본청 자산이고, 다른 하나는 여러 지자체가 채택한 외부 플랫폼이다. 재단 고유 자산처럼 쓰면 사실과 다르다([`spec/_proposal-delta.md`](../spec/_proposal-delta.md) §2 8번).

**그런데 지역관광공사 특별상은 해당 지역 기관이 자체 심사로 선정한다.** 즉 **자기 기관 이름이 잘못 적힌 문서를 그 기관이 직접 읽는다.**

**대응:**
- 발표·자료·화면에서 **그 기관명과 플랫폼명을 말하지 않는다.**
- 지역 논거는 두 가지로만 선다 → [`01_product_case.md`](./01_product_case.md) §4.
- **먼저 인정하는 쪽으로 정한다** — 감추다 지적받는 것보다 낫고, 지적하는 쪽이 그 기관 본인이다. 실제 문장은 [`spec/12`](../spec/12_judging_and_demo.md) §6.

### 4.3 청각장애 사용자에게 줄 것이 실질적으로 없다 (PD-2 닫힘 — 시각 경보기 채택)

> **★ 2026-09-01 결정: `visual_alarm`을 이번 범위에 넣는다** → [`spec/11`](../spec/11_open_items.md) **DEC-8** · [`spec/06`](../spec/06_suitability.md) §10.4.
> 등급은 P2b **`supporting`** 이다 — spec §4.2가 파생 항목의 `critical`을 금지하므로 `critical`로 올리지 않았다. **라벨은 여전히 바뀌지 않는다**(P2b의 critical 2개가 그대로다). 늘어나는 것은 **화면에서 실제로 읽을 수 있는 사실 하나**이고, 아래 문단이 이미 그 점을 정확히 적었다.

제출 제안서는 필요성 다섯 질문 중 하나로 **"청각장애인이 수어로 같은 백제를 만날 수 있는가"**를 넣고, 그 다섯이 그대로 서비스의 필요성이라고 못 박았다.

**구현에는 수어가 없다.** 그리고 구조적으로 더 나쁘다 — 청각장애 조건의 판정 필수 항목이 매우 적은데, 그 항목들이 바로 한국관광공사 자체 서비스도 필터를 제공하지 않는 필드다([`spec/03`](../spec/03_external_data.md) §2.1 참고 절). **조회하면 전부 "정보 없음"이 나올 가능성이 높다.**

**점자에 대해서는 강한 답이 이미 있다** — 점자정보단말기 사용자는 스크린리더와 함께 우리 HTML을 실시간 점역해 읽고 있으므로, 접근성 있는 HTML 자체가 점자 지원이다([`spec/01`](../spec/01_scope.md) §4.4 (2)). **수어에는 그런 답이 없다.**

**필요성을 다섯에서 넷으로 조용히 줄이는 것은 서면 심사에서 위험하다.** 제안서에 다섯이라고 적혀 있고 심사위원이 그걸 읽는다.

**먼저 분명히 할 것 — 이 문제에는 완전한 처방이 없다.**

수어 해설은 **콘텐츠 접근**의 문제이고, 아래 권고는 **안전 정보**의 문제다. **같은 장애 범주라는 이유로 하나가 다른 하나를 대체하지 않는다.** 그렇게 말하면 축소를 성과로 포장하는 것이 된다.

**그래도 할 수 있는 것:** [`spec/06`](../spec/06_suitability.md) §10.4가 **시각 경보기**를 "여유가 생기면 추가할 첫 번째 항목"으로 두고 추가 비용을 카탈로그 한 줄 + 등급표 한 줄 + 조사로 계산해 뒀다. **이걸 여유 항목에서 필수로 올린다.**

- 화재·비상 시 시각 경보기는 청각장애 사용자에게 **실재하는 안전 항목**이다.
- 한국관광공사 필드에 없으므로 콘텐츠 파일로 조사해 채운다 — **원 데이터가 비어 있어도 우리가 채울 수 있는 몇 안 되는 항목**이다.
- 청각장애 조건의 판정 근거가 늘어난다. 지금은 필수 항목이 매우 적고 그마저 대부분 비어 있다.

**이게 해결하지 못하는 것:** 수어 약속. 그건 그대로 미이행이고, [`spec/01`](../spec/01_scope.md) §4.1이 적은 이유(외부 기관 셋이 필요하다)가 답의 전부다. **"수어 대신 시각 경보기를 넣었습니다"라고 말하지 않는다** — 다른 과업이다.

**결정이 필요한 이유:** spec을 고치는 일이고, 관광지마다 조사 비용이 든다.

### 4.4 실사용자 검증 — "나중에"가 안 통하는 자리

제출 제안서는 **1단계(공모전 기간 내) 약속**에 단체 베타 테스트를 넣었다. [`spec/11`](../spec/11_open_items.md) §4는 실사용자 검증을 명시적으로 포기했다.

**차이가 큰 이유:** 발전 방향으로 미룬 것은 "아직 안 했다"로 설명되지만, **1단계 약속은 "이번에 하겠다"고 쓴 것**이라 미이행이 된다.

**말하는 방식:** 대체한 것을 먼저 말한다 — 자동 접근성 검사와 스크린리더 수동 검증을 실제로 했고, **판정 근거를 전부 공개해 사용자가 우리 판단을 검산할 수 있게 한 것**이 검증 부재에 대한 설계상의 대응이다. 그리고 [`spec/11`](../spec/11_open_items.md) §3b의 R-8을 **먼저 인정한다.**

### 4.5 도슨트 채널 수 — 세 곳에서 같은 숫자를 약속했다

제출 제안서가 도슨트를 여러 채널로 적었고, 같은 숫자가 문서 안에서 여러 번 반복된다. 구현은 그보다 적다.

**채널마다 이유가 다르다. 하나로 묶어 답하지 않는다.**

| 약속한 채널 | 구현 | 왜 |
|---|---|---|
| 음성 | **있다** | 한국관광공사가 완성된 오디오를 준다 |
| 자막(대본) | **있다** | 같은 API가 대본 전문을 준다. **접기 가능하되 DOM에서 사라지지 않는다** ([`spec/07`](../spec/07_screens.md) S6 규칙 2) |
| 점자 | **별도 기능으로 안 만든다** | 축소가 아니라 재정의다 → §4.3 |
| 수어 | **없다** | 외부 기관 셋이 필요하다 ([`spec/01`](../spec/01_scope.md) §4.1). **미이행이 맞다** |

**세 번째와 네 번째를 같은 말로 답하면 안 된다.** 점자에는 "이미 읽히고 있다"는 강한 답이 있고, 수어에는 없다. 앞 판은 이 절에서 점자 논리를 다시 꺼내 도슨트 채널 질문에 답하지 않은 채 넘어갔다.

**결정:** 발표·자료에서 **채널을 숫자로 세지 않는다.** 무엇이 있고 무엇이 없는지 이름으로 말한다 — 숫자는 확인당하고, 이름은 위 표대로 각각 답이 있다.
