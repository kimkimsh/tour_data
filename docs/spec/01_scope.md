# 01 — 범위 (만드는 것 / 안 만드는 것)

> 범위 다툼이 생기면 이 문서로 돌아온다. 여기 없는 것은 안 만드는 것이다.

---

## 1. 한 줄 정의

> 충남 공주·부여 백제역사유적지구 **6개 관광지**에 대해, 사용자가 자기 이동 조건을 고르면 **한국관광공사 무장애 데이터를 근거까지 펼쳐 보여주는 판정 카드**를 주고, 현장에서는 **단계별 경로 안내와 오디오 도슨트**를 주고, 방문 후에는 **기록을 인쇄 가능한 문서로** 만들어 주며, 같은 데이터의 빈칸을 **개선 우선순위 리포트**로 되돌려 주는 웹앱.

> **중요한 리스크:** 이 6곳이 한국관광공사 **무장애여행 서비스(KorWithService2)에 등록돼 있는지 아직 확인되지 않았다.** 이것이 프로젝트 전체를 좌우한다. 착수 첫날 확인한다 → `11_open_items.md` **P0-1**.

## 4. 안 만드는 것 — 그리고 왜

이 목록은 **"발전 방향"이 아니라 "이번에 안 만드는 것"** 이다. 제안서에는 이미 들어가 있는 항목이 많으므로, 발표에서는 "구현 범위"와 "발전 방향"을 말로 구분해서 설명해야 한다.

### 4.1 물리적으로 불가능해서 뺀 것 (현장 답사·외부 인력 필요)

| 항목 | 왜 못 하나 |
|---|---|
| 경사도(%)·단차 높이(mm)·휠체어 회전반경 실측 | 공주·부여에 가서 줄자와 경사계로 재야 한다 |
| 출입구별 실측 사진 | 현장 촬영 필요. 대신 한국관광공사 관광사진갤러리와 공식 사진을 쓴다 |
| "현장 검증 완료" 표기 + 2차 승인 절차 | 검증자 본인 1명뿐. 2차 승인자가 존재하지 않는다 |
| 수어 영상 채널 | 국립국어원 개별 클립 라이선스 확인 + 다누림 협약 + 수어 전문가 키워드 선정 + 촬영. 외부 기관 3곳이 필요하다 |
| 점자 파일(.brf) 생성과 검수 | 점자 전문가와 엠보서가 없다. **대안도 만들지 않는다** — 이유는 §4.4 (2) |
| 충남교육청 체험학습 서식 1:1 정합 PDF | 서식 원본을 정보공개청구로 받아야 한다 |
| 마스코트 6컷 일러스트 | 외주 제작 필요 |
| 충남문화관광재단·다도라·올담 연동 | 기관 협약 필요. 리포트는 **CSV 내려받기**까지만 만든다 |
| 관광약자·특수교육 전문가 사용성 검증 | 모집·보상·장소 섭외 필요 |
| 실제 이용자 3회차 검증 프로토콜 | 위와 동일 |

### 4.2 기간 대비 비용이 커서 뺀 것

| 항목 | 대신 무엇을 하나 |
|---|---|
| 다국어 4종(한/영/일/중) 전체 UI | **UI는 한/영 2종.** 관광지 제목·개요는 한국관광공사 일문·중문 API로 4종 다 저장해 두고 상세 화면에서만 노출 |
| 도슨트 3가지 모드(어린이/어른/쉬운 글) | **원문 + 쉬운 글 2가지.** 쉬운 글은 사람이 직접 다듬어야 하므로 A등급 2곳만 |
| 실시간 알림(Supabase Realtime) | 제보가 즉시 공개되므로 페이지 열 때 조회하면 된다. 트리거·브로드캐스트·구독 생명주기 전부 불필요 |

| 벡터 검색 / RAG / 임베딩 / OCR / 360° / AR | 이번 서비스 기능과 무관 |

| 후기 작성 / 사용자 GPX 제출 | 제보(S7)를 유일한 사용자 입력 창구로 둔다 |

### 4.3 법적 의무를 줄이려고 의도적으로 뺀 것

이건 "못 해서"가 아니라 **"안 하는 게 이득이라서"** 뺐다.

| 안 하는 것 | 사라지는 의무 |
|---|---|
| 브라우저 위치 정보(`navigator.geolocation`) **일절 사용 안 함** | 개인위치정보를 수집하지 않으므로 **위치기반서비스사업자에 해당하지 않는다** — 신고·보호책임자 지정·접근 기록 보관 의무가 모두 발생하지 않는다. **조문 번호는 확인 후 인용한다** ([`08_accessibility_legal.md`](./08_accessibility_legal.md) §2.4) |
| 제보에 좌표 저장 안 함 | 위 항목과 동일 + 좌표 삭제(제23조) 절차 불필요 |
| 결제·예약·중개 없음 | 통신판매업 신고 / 여행업 등록 불필요 |
| 회원가입 없음(익명 인증만) | 수집하는 개인정보가 제보 본문과 익명 식별자(UUID)뿐 |
| AI 생성 콘텐츠 **원칙적으로 없음** | 인공지능기본법 제31조 표시 의무 최소화. 단, 기기 음성 합성(TTS)을 쓰는 경우에만 "기기 음성 합성" 표시 (자세히는 [`08_accessibility_legal.md`](./08_accessibility_legal.md)) |

**대신 반드시 해야 하는 것:**
- 개인정보 처리방침 (`/privacy`)
- 공공누리 출처 표기 (푸터 + `/credits` + 이미지별)
- 저작권 3유형(`cpyrhtDivCd=Type3`) 이미지 **변형 금지** 처리

### 4.4 기존 계획을 바꾼 판단 — 그리고 그 이유

여기 3가지는 "줄인 것"이 아니라 **"더 나은 방법으로 바꾼 것"** 이다.

#### (1) PDF 라이브러리 → 브라우저 인쇄

기존 계획은 학생용 PDF에 `pdf-lib`, 쉬운 글 PDF에 `@react-pdf/renderer`를 쓰기로 했다. 이 조합은 알려진 함정이 많다.

- `@react-pdf/renderer`의 한글 폰트 등록은 웹 절대경로(`/fonts/...`)로는 실패하고 `process.cwd()` + `outputFileTracingIncludes` 설정이 둘 다 맞아야 한다
- 한중일 문자에 줄바꿈 규칙이 없어 `registerHyphenationCallback`을 따로 넣어야 한다
- Pretendard 폰트에 **한자 글리프가 없어서** 사적 지정번호의 한자가 깨진다
- `pdf-lib`은 서식 필드가 없는 PDF에 대비한 좌표 오버레이 대체 경로가 또 필요하다

**바꾼 방법: 인쇄용 CSS를 입힌 HTML 페이지(`/diary/print`)를 만들고, 사용자가 브라우저의 "인쇄 → PDF로 저장"을 쓴다.**

이게 더 나은 이유:
- 웹 접근성 기준에서 **HTML이 원래 정답**이다. PDF 전용 화면은 KWCAG에서 감점 요인이고, 기존 계획도 "모든 PDF에 HTML 대안을 반드시 함께 제공"이라고 못 박아 뒀다. 그렇다면 HTML만 만들면 된다
- 한글·한자 폰트 문제가 원천적으로 없다 (브라우저 폰트를 쓴다)
- 스크린리더로 읽을 수 있다
- 구현 비용이 1/10

#### (2) 점자 — 별도 기능으로 만들지 않는다

기존 계획은 `braillify` 라이브러리로 유니코드 점자(U+2800)를 만들고 다시 점자 ASCII로 변환해 `.brf`(점자 프린터용 파일)를 만들기로 했다. 이건 만들 수 없다:

- **한국점자규정은 초성·중성·종성 + 약자 34개 + 약어 체계**라 영어 점역기로는 옳게 변환되지 않는다. **잘못된 점역 파일은 없느니만 못하다**
- 검수해 줄 점자 전문가와 엠보서(점자를 종이에 찍는 프린터)가 없다
- 참고로 `braillify` 2.0.1이 실제로 내보내는 함수는 `encode`/`translateToUnicode`/`translateToBrailleFont`이고, 기존 계획서 두 곳이 쓴 `translate`/`braillify`는 **존재하지 않는 함수다**

**그럼 텍스트(.txt)로 대신 주면 되지 않나 → 그것도 아니다.**

**점자정보단말기 사용자는 이미 우리 HTML을 점자로 읽고 있다.** 스크린리더와 점자 디스플레이가 화면 내용을 실시간으로 점역하기 때문이다. 여기에 `.txt` 파일을 하나 더 얹는 것은 **거의 아무것도 추가하지 않으면서 "점자 지원"이라는 이름만 얻는 것**이다. 그건 포장이다.

**그래서 이렇게 한다:**

| 결정 | 내용 |
|---|---|
| **점자를 기능 목록에서 뺀다** | "점자 채널", "점자 호환 텍스트" 같은 표현을 쓰지 않는다 |
| **진짜 점자 지원 = 접근성 있는 HTML** | 이건 [`08_accessibility_legal.md`](./08_accessibility_legal.md) §1이 전부 다룬다. NVDA 수동 검증(§1.4)이 이걸 확인한다. **별도 기능으로 세지 않는다 — 중복 계상이다** |
| 도슨트 대본 `.txt` 내려받기 | **삭제.** 대본은 이미 화면에 HTML로 있다. 복사하면 된다 |
| 여행 기록 `.txt` 내보내기 | **유지하되 이름을 바꾼다** → "텍스트로 내보내기". 메모 앱·이메일·기기 이동용이고, 점자와 무관한 일반 기능이다 |
| 정식 점자 지원 | **발전 방향.** 한국점자규정 기반 점역 + 점자 전문가 검수 + 엠보서 출력 검증이 한 묶음이다. 셋 중 하나만 해서는 안 된다 |

> **제안서와의 차이 — 기획 수정 시 반영 필요.** 제안서는 도슨트를 **"음성·자막·점자·수어 4채널"** 로, 다이어리를 **"점자 .brf 포함 6채널"** 로 적었다. 실제 구현은 **음성·자막 2채널**이고 점자·수어는 발전 방향이다. 발표에서 "4채널"이라고 말하면 심사에서 확인당한다.

#### (3) 적합도 산식의 7번째 축 삭제

기존 산식의 Layer A는 7개 축이고 그중 `verifiedUgc`(검증된 사용자 제보)가 0.07을 차지한다. 그런데 **제보가 하나도 없을 때 이 축의 값이 무엇인지 어디에도 정의돼 있지 않다.** 출시 직후에는 항상 이 상태다.

**바꾼 방법: 축을 6개로 줄이고 가중치를 재배분한다.** 사용자 제보는 점수 축이 아니라

- 상세 화면의 **경고 배너**로,
- 해당 항목의 **최근 확인일 갱신(데이터 신뢰도에 반영)** 으로

반영한다. 데이터가 쌓일수록 좋아지는 구조는 그대로 유지되면서, 정의되지 않은 값이 사라진다. 자세한 수치는 [`06_suitability.md`](./06_suitability.md) §3.

#### (4) 제보 — 검수 대기 없이 즉시 공개하고, 사진은 받지 않는다

기존 계획은 제보를 **승인 후 공개**하고, 승인 시 해당 항목의 확인일을 갱신하고, 상세 화면에 경고 배너를 띄우는 구조였다. 이걸 바꿨다.

**바꾼 것 (1) — 제보는 댓글처럼 바로 보인다.**

| | 기존 | 지금 |
|---|---|---|
| 흐름 | 제보 → 대기 → 관리자 승인 → 공개 | **제보 → 즉시 공개** |
| 상태 | `pending` / `approved` / `rejected` | `is_hidden` 불리언 하나 |
| 관리자 역할 | 사전 검수(전부 봐야 함) | **사후 조치** — 부적절한 것만 숨김 |
| 점수 반영 | 승인 시 확인일 갱신 | **점수에 안 들어간다** |

**왜:** 확인된 사실과 방문자 발언은 성격이 다르다. 섞으면 둘 다 신뢰를 잃는다.

- `data_snapshots` = 우리가 **출처를 대고 확인한 것**
- `barrier_reports` = 방문자가 **한 말**

화면에서도 시각적으로 분리하고, 적합도 점수는 스냅샷만 본다. 제보가 사실이 되는 통로는 **사람이 검토해 `content/curated-facts.json`에 옮겨 적고 커밋하는 것** 하나뿐이다. 그때 출처 칸에 제보 ID를 남기면 `git log`가 판단 기록이 된다.

이 변경으로 **기존 계획의 모순 하나가 통째로 사라졌다** — "승인된 제보가 확인일을 갱신하되 상태는 못 뒤집는다"는 규칙이 두 문서에 서로 다르게 적혀 있었고, 저장 구조상 "서로 다른 제보자 2건 이상"을 표현할 수도 없었다.

**바꾼 것 (2) — 제보 사진을 받지 않는다.**

즉시 공개로 바뀌면서 사진의 위험/이득 비율이 뒤집혔다.

| | 사전 검수가 있을 때 | 즉시 공개일 때 |
|---|---|---|
| 사진에 사람 얼굴이 찍힘 | 관리자가 거른다 | **바로 공개된다.** 초상권 문제고 되돌릴 수 없다 |
| 부적절한 이미지 | 관리자가 거른다 | 누군가 볼 때까지 떠 있다 |
| 구현 비용 | 저장소 버킷 + EXIF 제거 + MIME 검증 + 서명 URL + 뷰어 ≈ 하루 | 같음 |

**텍스트만으로도 제보의 목적(다음 방문자에게 알림)은 달성된다.** "엘리베이터 고장 · 2026-09-10 · 동문 쪽 계단 보수 공사로 통행이 막혀 있습니다" — 이거면 충분하다.

빼면 하루치 작업이 사라지고 초상권·개인정보 위험이 0이 된다.

> **제안서와의 차이 — 기획 수정 시 반영 필요.** 제안서는 "**사진과 선택형 양식으로 제보**"하고 "**검수 화면을 거쳐** 후속 사용자에게 안내"한다고 적었다. 실제 구현은 **텍스트 제보 · 즉시 공개 · 사후 숨김**이다.
