# 04 — 남은 것

> **한 줄:** 코드는 다 있고 게이트도 다 통과한다. **막혀 있는 것은 전부 하나의 원인이다 — 한국관광공사 서비스 키가 없고 Supabase 프로젝트가 없다.** 그 둘이 생기면 아래 1절이 거의 통째로 닫힌다.
>
> 여기에 적힌 것 가운데 **코드를 더 써야 닫히는 항목은 3절뿐이다.** 1·2절은 실행하면 닫히거나, 실행해 보고서야 무엇을 고쳐야 할지 알 수 있는 것들이다.

## 1. 키가 없어서 막힌 것

### 1.1 P0 탐침 11건 — 하나도 실행되지 않았다

`scripts/probe.ts`는 완성돼 있고, 키 없이 실행하면 조용히 통과하지 않고 종료 코드 1로 죽는다.

```
$ pnpm probe
ingest: KTO_SERVICE_KEY_DECODING is not set. Put the DECODING form of the key in
.env.local — the ENCODING form is re-encoded by URLSearchParams and the gateway
answers resultCode 30.
```

| 항목 | 답이 안 나온 것 | 답에 따라 달라지는 것 |
|---|---|---|
| **P0-1 ★★★** | 6곳이 무장애여행 데이터셋에 등록돼 있는가, 24항목 중 몇 개가 채워져 있는가 | **프로젝트의 형태 전체.** 등록이 0곳이면 갭 리포트가 주 화면이 되고 적합도는 부차가 된다 |

P0-7(백제역사유적지구 구성자산 여부)은 사람이 국가유산청 포털에서 확인해 이미 닫혔고, P0-8은 매뉴얼 v4.2로 해소됐다.

### 1.2 `resolveStatus()`가 실제 문장 144개를 어떻게 판정하는지

`11_open_items.md` **O-1**이 1주차 작업으로 잡아 둔 것이고, **이번 라운드에서 우선순위가 올라갔다.**

이 함수는 이번에 두 번째로 방향이 뒤집힌 곳이다([`06_review_round.md`](./06_review_round.md) S1–S3). 42건의 회귀 테스트를 붙였고 전부 실제 문장이지만, **그 42건은 우리가 아는 문장이다.** 6곳 × 24항목 = 144개의 실제 응답에는 우리가 본 적 없는 어휘가 있다.

**키가 생기면 먼저 할 일:** `pnpm ingest --only=accessibility --dry-run`을 돌리고, 144개 원문과 판정 결과를 나란히 출력해 눈으로 대조한다. 규칙만 보고는 어떤 문장이 어디로 가는지 알 수 없다.

특히 확인해야 할 것:
- 장애물 명사 사전(`단차`·`문턱`·`계단`·`장애물`·`급경사`·`경사(?!로)`·`돌길`·`자갈`·`비포장`·`협소`·`좁음`)에 빠진 단어
- 8자 근접 창(`NEARBY_WINDOW`)이 실제 문장 길이에 맞는지 — `단차가 거의 없는 편입니다` 같은 문장은 창을 넘길 수 있다
- 조건부 사전에 `어려움`을 넣은 판단. `진입 어려움`을 `partial`로 읽는데, 문맥에 따라 `unsupported`가 맞을 수 있다

### 1.3 `readThemeCoord()`가 실제로 좌표를 읽어내는가

**매뉴얼에 `themeBasedList`의 좌표 필드가 문서화돼 있지 않다.** 도슨트 경로 전체가 이 함수에 걸려 있고, 좌표가 없으면 반경 매칭이 작동하지 않아 6곳 어디에도 도슨트가 붙지 않는다. 도슨트 화면이 비는 것으로 조용히 나타난다.

### 1.4 이미지 URL의 https 형태가 실제로 열리는가

`resolveImageUrl()`이 HEAD로 확인하고 안 열리면 `/api/image-proxy`로 저장한다(D-18). **그 분기가 실제로 어느 쪽으로 가는지는 실행해야 안다.** 프록시 쪽으로 간다면 이미지가 전부 우리 서버를 거치게 되고, 그건 Vercel 함수 실행 시간과 대역폭에 영향이 있다.

## 2. Supabase가 없어서 막힌 것

### 2.1 `pnpm validate:content`가 지금 빨간불이고, 그래서 CI도 빨간불이다

```
$ pnpm validate:content
content validation failed:
  - pois.json: 6 place(s) still carry ktoContentId "UNRESOLVED"
    Run `pnpm probe` (P0-1) with a KTO service key, then copy the confirmed ids in.
```

**의도된 실패다.** 확인되지 않은 `contentId`로 배포하면 조용히 다른 관광지의 무장애 데이터를 수집한다. `11_open_items.md` P0-1이 이전 기획 문서에 서로 다른 세 세트가 있었다고 경고했고, 그중 어느 것도 쓰지 않았다.

이 검사를 끄거나 지우지 않았다. **켜 두고 통과만 하는 검사는 없는 것보다 나쁘고, 지금 빨간불인 것이 프로젝트 상태에 대한 정확한 보고다.**

### 2.2 화면 위에서 검증되지 않은 제보 흐름

DB가 없어서 **브라우저에서** 확인하지 못한 것:

- 제보 등록 → 즉시 공개 (S7 완료 기준 D-6)
- 관리자 숨김 → 다른 사용자 화면에서 사라짐
- 익명 인증이 실제로 켜져 있는지 — **대시보드와 `config.toml` 양쪽에서 따로 켜야 한다**
- 캐시 무효화가 실제로 몇 초 안에 반영되는지
- 컬럼 단위 권한이 **PostgREST를 통해서도** 같게 동작하는지. 스텁 Postgres에서는 확인했지만([`05_verification.md`](./05_verification.md) §3.4) PostgREST가 그 오류를 어떤 HTTP 코드로 바꾸는지는 확인하지 못했다 — `/api/report`가 502로 처리할 것이고, 그건 「제보를 올리지 못했습니다」로 보인다

**제보 제출에는 자동 검사가 하나도 없다.** 골든 플로우는 조건 → 목록 → 상세 → 근거 → 경로 → 갭 리포트까지만 덮는다. axe가 `/ko/report`를 훑지만 그건 폼이 접근 가능한지만 본다.

DB 없이는 통과할 수 없는 검사이므로 지금 쓰지 않았다. **끄거나 `skip`한 것이 아니라 아직 쓰지 않은 것이고, 그 차이를 여기 적어 둔다** — 「빨간불로 서 있는 검사」와 「없는 검사」는 다르고, 후자가 더 나쁘다. §5의 순서 8번에서 Supabase와 함께 써야 한다:

- 익명 세션 생성 → 5컬럼 insert → 관광지 화면의 제보 절에 즉시 나타남
- 같은 날 같은 (관광지, 분류) 두 번째 제출 → 409 → 화면의 「같은 날에는 같은 제보를 한 번만」 문구
- 확인 패널이 포커스를 받고 `role="status"`로 읽히는지(D-16)
- 관리자 숨김 → 다른 사용자 화면에서 사라짐

### 2.3 첫 `db push` 이후에는 마이그레이션을 고칠 수 없다

**지금은 해당 없고, 첫 배포 직후부터 해당된다.** 이번 라운드에서 `002_reports.sql`을 여러 번 제자리에서 고쳤다 — 컬럼 권한, `revoke all`, 정렬 인덱스. 그게 가능한 이유는 **이 스키마가 한 번도 push되지 않았기 때문**이다: `supabase/` 전체가 untracked이고, `supabase/.temp`도 `.branches`도 없어 연결된 프로젝트가 없으며, 리포지터리 어디에서도 `supabase_migrations.schema_migrations`를 참조하지 않는다.

**한 번 `supabase db push`를 하면 그 원장이 `002`를 적용됨으로 표시하고 다시 실행하지 않는다.** 그 뒤로 이 파일을 고치는 것은 배포된 DB에 아무 일도 하지 않는다 — 정렬 인덱스 교체 같은 변경이 조용히 무효가 된다. 그때부터는 `003_*.sql`을 새로 써야 한다.

### 2.4 `supabase/seed.sql`이 이제 슈퍼유저 전용이다

컬럼 권한을 좁힌 결과다. `supabase db reset`이 이 파일을 `postgres`로 실행하므로 지금 깨지지 않지만, **누군가 이 시드를 `authenticated`로 돌리려 하면 `permission denied`가 난다.** 시드는 개발 편의이고 앱 경로가 아니므로 이대로 두지만, 알고 두는 것과 모르고 두는 것은 다르다.

## 3. 코드를 더 써야 닫히는 것

여기가 유일하게 「구현이 남았다」고 말할 수 있는 절이다.

### 3.1 기상 특보 원천이 없다 — `weather_warning`은 모든 곳에서 `unknown`이다

32개 항목 중 하나가 **영구히 비어 있다.** `ContextPayload.weather`는 스키마에 있지만 `buildContext`는 `{crowd, visitors, fetchedAt}`만 쓰고, 기상청 호출이 리포지터리 어디에도 없다.

`context` 축(가중치 0.10)에 4항목 중 1항목이 고정 0.35로 들어간다. 이제 ingest가 실행마다 이 사실을 경고로 남긴다:

```
warn  no weather source is wired: weather_warning is unknown for every place
```

**두 선택 중 하나가 필요하다.** (a) 기상청 특보 API를 붙인다 — 4주 범위에서는 새 외부 의존 하나가 늘어난다. (b) 이 항목을 카탈로그에서 빼고 32 → 31로 줄인다 — 스펙 §4.1이 32를 못 박고 있으므로 스펙 개정이 필요하다. **이건 사람이 결정할 일이다.**

### 3.2 인쇄물의 페이지 번호

Chrome은 `@page` 마진 박스를 구현하지 않아 `counter(page)`를 인쇄할 수 없다. 반복 각주는 `position: fixed` 스트립으로 해결했지만(`.print-running-footer`), **페이지 번호는 CSS만으로는 방법이 없다.** JS로 페이지 높이를 계산해 번호를 심는 것이 유일한 경로이고, 4주 범위에서는 하지 않는 편이 낫다고 판단했다.

### 3.3 `labelEn` 32개가 검토되지 않았다

카탈로그에 영어 라벨을 추가한 것은 스펙에 없는 것이다(D-7). **번역을 사람이 검토하지 않았다.** `Tactile paving`(점자블록), `Room for deaf guests`(객실(청각)) 같은 것들은 국제적으로 통용되는 표현을 골랐지만, 확인받지 않았다.

같은 문제가 새로 생긴 것들에도 있다: `statusLabel`/`absenceLabel`의 영어(`Partly available`, `Structural constraint (confirmed)`), `admin` 네임스페이스의 영어(관리자 화면은 `ko` 고정이므로 실제로 쓰이지는 않는다).

### 3.4 인쇄되는 여행 기록이 `/en`에서도 한국어다

`src/domain/diary.ts`가 라벨을 한국어로 하드코딩한다. `/en/diary/print`는 영어 UI 안에 한국어 문서를 출력한다. axe는 잡지 못한다 — 문서 자체는 유효하다.

**고치려면** `buildDiaryDocument`가 로케일을 받아야 하고, 그러면 `diaryToText`와 GPX 내보내기도 같이 받아야 한다. 작지 않은 변경이고, 이번 라운드의 다른 결함보다 비용이 크다고 판단해 넘겼다.

## 4. 사람이 결정할 것

### 4.1 부소산성 `elevator: unsupported` 판단

`content/curated-facts.json`에 부여군 공식 편의시설 표의 「없음」을 근거로 `unsupported`를 넣었다. **`not_applicable`로 읽는 것도 방어 가능하다** — 야외 산성에 엘리베이터가 없는 것은 시설 부재라기보다 구조 제약이다.

지금 상태에서는 P1a/P1b에게 `elevator`가 critical이므로 이 한 줄이 부소산성의 판정을 「대체추천」 쪽으로 끌어당긴다. `not_applicable`로 바꾸면 분모에서 빠지고 점수가 오른다. **어느 쪽이 방문자에게 정직한가는 도메인 판단이고, 근거 문장을 붙여 명시해야 한다.**

### 4.2 무장애 인증 행을 전부 뺀 것

공개 출처가 예비/본만 구분하는데 스키마 enum은 예비/일반/우수를 원한다. 그리고 확인된 인증은 전부 **부속 건물**(방문자센터, 화장실)에 대한 것이어서, 그대로 넣으면 Layer C가 관광지에 건물의 인증을 얹는다. 그래서 무령왕릉의 `open_tourism` 한 줄만 넣었다.

**Layer C가 사실상 죽어 있다.** 스펙 §5의 인증 보정이 6곳 중 1곳에만, 그것도 열린관광지 쪽으로만 적용된다. 인증 데이터를 제대로 넣을지, Layer C를 스펙에서 내릴지는 사람이 결정할 일이다.

### 4.3 `flag_report`를 `anon`에게 열어 둔 것

검토가 남긴 지적이다. `flag_report`는 자기 일만 하고(첫 신고 시각만 세팅, 반환값 없음, 숨겨진 제보는 건드리지 않음) 그 부분은 확인됐다. 그런데 **`anon` 호출자가 모든 제보를 신고할 수 있다.** 그러면 관리자 목록의 기본 정렬 인덱스 `((flagged_at is not null) desc, created_at desc)`가 신호를 잃는다 — 전부 신고된 상태가 되므로.

**스펙 §5.3의 카운터 논거와 같은 결과를, 깊이가 아니라 너비로 달성한 것이다.** 카운터를 두지 않은 이유가 「소수의 신고로 제보를 묻을 수 있다」였는데, 전부 신고하면 정렬이 무의미해져서 같은 곳에 도달한다.

**세 선택.** (a) 그대로 둔다 — 실제 공모전 심사 기간에 이런 공격이 올 가능성은 낮다. (b) `authenticated`로만 좁힌다 — 제보를 올리려면 어차피 익명 세션이 필요하므로 일관되고, 세션 없는 방문자는 신고할 수 없게 된다. (c) 신고에도 하루 1건 인덱스 같은 것을 둔다 — 테이블이 하나 늘어난다.

**스펙이 `to anon, authenticated`를 명시하고 있으므로 바꾸지 않았다.** (b)가 비용 대비 효과가 가장 좋아 보이지만 스펙 개정이 필요하다.

**4라운드 검증이 이 항목의 결과를 하나 더 찾았다.** 관리자 기본 화면은 `sort=flagged`이고 `.limit(200)`에 페이지네이션이 없다. 신고된 제보가 200건을 넘으면 **기본 화면이 신고된 것만 보여준다** — 실측: 264건 신고 상태에서 상위 200행 전부가 신고된 행이고 신고되지 않은 첫 행의 위치가 `NULL`이다. 운영자는 `?sort=recent`로 옮기지 않는 한 새로 올라온 제보를 **하나도 볼 수 없다.**

즉 전부 신고하는 것은 정렬 신호만 죽이는 게 아니라 **기본 화면에서 신고되지 않은 제보를 전부 밀어낸다.** 심사 규모(제보 3건)에서는 일어나지 않고, 내가 고른 정렬의 당연한 결과이므로 바꾸지 않았다 — 다만 (b)를 고를 이유가 하나 더 늘었다. 페이지네이션을 붙이는 것도 같은 문제를 완화한다.

## 5. 닫힌 순서

키가 생기는 날의 순서다. 각 단계가 그 앞 단계에 의존한다.

```
1. pnpm probe                  → P0 11건, 특히 P0-1
2. content/pois.json 의 UNRESOLVED 6개를 확정 id로 교체
3. pnpm validate:content       → 여기서 초록불이 되어야 CI가 초록불이 된다
4. pnpm ingest --dry-run       → 144개 원문과 resolveStatus 판정을 눈으로 대조 (§1.2)
5. resolveStatus 규칙 조정 + tests/resolve-status.test.ts 에 실제 문장 추가
6. Supabase 프로젝트 + 익명 인증 켜기 + 마이그레이션 2개
7. pnpm ingest                 → 실제 스냅샷
8. 제보 흐름 E2E를 쓴다 (§2.2) + pnpm e2e 전부
9. NVDA 수동 검증 (§4.4)
```

4번과 5번 사이에서 멈추게 될 가능성이 가장 높다. **거기서 나오는 것은 코드 버그가 아니라 어휘 목록이고, 그건 실제 문장을 보기 전에는 쓸 수 없다.**
