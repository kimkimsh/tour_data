# 07 — main 병합과 인수인계

> **한 줄:** 브랜치 2개를 `main`에 넣고 지웠다. 그리고 **막혀 있던 것 중 「사람이 해야 하는 부분」을 실제로 할 수 있는 형태로 바꿨다** — `docs/guide/` 5개 문서.
>
> 코드는 안 고쳤다. 죽은 환경변수 한 줄만 지웠다.

---

## 1. 브랜치 정리

### 하기 전

```
main                       c1b2249
  └ docs/spec-plan-review-v7  f977f7a   (+2 커밋, 원격과 동기화됨)
      └ feat/app-implementation  232b431   (+8 커밋)
```

세 브랜치가 **한 줄로** 이어져 있었다. 갈라진 곳이 없어서 두 병합 다 fast-forward였다 — 병합 커밋 없이 `main`이 앞으로 간 것뿐이다.

### 순서

```bash
git switch main
git merge --ff-only docs/spec-plan-review-v7      # main → f977f7a
git merge --ff-only feat/app-implementation       # main → 232b431
git push origin main                              # ★ 지우기 전에 푸시
git branch -d docs/spec-plan-review-v7 feat/app-implementation
git push origin --delete docs/spec-plan-review-v7 feat/app-implementation
```

**푸시가 삭제보다 먼저다.** 반대로 하면 원격에 없는 커밋을 지우는 것이 된다. 그리고 지우기 전에 두 브랜치가 정말 `main`에 다 들어갔는지 `git merge-base --is-ancestor`로 확인했다 — `git branch -d`도 같은 검사를 하지만, 지우는 명령이 스스로 안전을 판정하게 두는 것보다 먼저 물어보는 편이 낫다.

`--ff-only`를 쓴 이유: 병합 커밋을 만들지 않겠다는 뜻이 아니라, **fast-forward가 아니면 실패하라**는 뜻이다. 예상과 다른 상태였으면 조용히 병합 커밋을 만드는 대신 멈춘다.

### 결과

```
$ git branch -vv
* main  232b431 [origin/main]

$ git branch -r
  origin/HEAD -> origin/main
  origin/main
```

로컬·원격 모두 `main` 하나. 커밋 10개가 전부 들어갔고 작업 트리는 clean이다.

## 2. 죽은 환경변수 하나 삭제

`.env.example`에 **`NEXT_PUBLIC_KAKAO_MAP_JS_KEY`**가 있었는데 **코드 어디서도 읽지 않는다.**

```bash
$ grep -rhoE "process\.env\.[A-Z_0-9]+" src scripts | sort -u
# 목록에 KAKAO 없음
```

지도를 넣지 않기로 했고(DEC-2, 목록 방식), 경로 안내의 카카오 링크는 **URL 스킴**(`m.map.kakao.com/scheme/route`)이라 JS 키가 필요 없다.

**이걸 남겨 두면 안 되는 이유가 지금 생겼다.** 이번에 「어떤 키를 받아야 하는가」 문서를 쓰는데, 그 목록에 이게 들어가면 **쓰지도 않을 카카오 개발자 등록을 하러 가게 된다.** 문서를 쓰다가 발견한 것이고, 문서에 넣기 전에 지웠다.

## 3. `docs/guide/` — 5개 문서

막혀 있는 것의 원인은 [`04_open_items.md`](./04_open_items.md)에 이미 정확히 적혀 있었다. 그런데 그 문서는 **「무엇이 왜 막혔는가」**를 적은 것이지 **「그래서 어떻게 푸는가」**를 적은 게 아니다. 그 간극을 메운 것이다.

| 문서 | 답하는 질문 |
|---|---|
| `00_README.md` | 뭘 받아야 하나, 어느 순서로 |
| `01_kto_api_key.md` | 공공데이터포털에서 API 6개 신청 → 키를 `.env.local`에 |
| `02_supabase.md` | 프로젝트 생성 → 익명 로그인 → 값 3개 → 마이그레이션 → 관리자 계정 |
| `03_first_run.md` | probe → id 채우기 → 검증 → **문장 144개 대조** → 수집 |
| `04_decisions.md` | 사람이 정해야 하는 5가지 |

### 문서에 앞세운 함정 세 개

전부 **조용히 실패하는** 것들이라 앞에 뺐다.

**1. 한국관광공사 키는 Decoding 쪽을 써야 한다.** Encoding 쪽을 넣으면 `resultCode 30 등록되지 않은 서비스키`가 오는데, 이 메시지가 사람을 속인다 — 키를 다시 발급받으러 가게 만든다. 키는 멀쩡하고 형태만 틀린 것이다. (환경변수 이름을 `KTO_SERVICE_KEY_DECODING`으로 길게 지은 이유이기도 하다.)

**2. Supabase 익명 로그인은 두 군데서 따로 켠다.** `config.toml`에 이미 `true`로 있지만 그건 로컬 전용이고, 웹 대시보드에서 한 번 더 켜야 한다. 파일에 써 있으니 됐겠지 하고 넘어가면 **제보 버튼이 아무 반응도 안 한다.**

**3. `db push` 이후에는 마이그레이션 파일을 못 고친다.** Supabase가 「적용됨」으로 기록하고 다시 실행하지 않는다. 이번 작업에서 `002_reports.sql`을 네 번 고쳤는데, **그게 가능했던 유일한 이유가 아직 push를 안 했기 때문**이다. 그래서 가이드는 웹 SQL Editor에 붙여넣는 방법을 기본으로 안내한다 — 그쪽은 원장을 남기지 않는다.

### 문서에 넣은 명령은 전부 실행해서 확인했다

`03_first_run.md`의 문장 대조 스니펫도 돌려 봤다:

```
$ python3 -c "..."
detail 있는 행: 54
supported    | 출입구까지 경사로가 설치되어 있음
partial      | 경사로로 이루어져 있으나 흙구간 및 일부구간 접근 어려움
```

**안 도는 명령을 문서에 넣지 않는 것이 이 폴더의 규칙이다.**

## 4. 결정 5가지 — 숫자를 계산해서 붙였다

[`04_open_items.md`](./04_open_items.md) §4는 「이건 사람이 정할 일」이라고만 적어 두었다. **그것만으로는 정할 수가 없다** — 고르면 무엇이 얼마나 바뀌는지가 없으니까.

그래서 각 선택지를 **지금 데이터로 실제 계산**해서 붙였다.

### 4.1 부소산성 엘리베이터 — 라벨이 바뀐다

휠체어 이용자(P1a) 기준으로 `calculateSuitability`를 두 번 돌렸다:

| | 라벨 | 점수 | 막힌 항목 | KTO 분모 |
|---|---|---|---|---|
| 지금 (`unsupported`) | **대체추천** | 39 | `elevator` | 22 |
| `not_applicable`로 바꾸면 | **주의** | 42 | 없음 | 21 |

**점수 3점은 중요하지 않고 라벨이 바뀌는 게 중요하다.** 「다른 곳 권장」과 「확인하고 가세요」는 방문자에게 완전히 다른 말이다.

### 4.2 기상 특보 — 빼도 점수가 거의 안 움직인다

6곳 전부 계산:

```
공산성 41→41   무령왕릉 54→55   공주박물관 53→53
부소산성 39→39  정림사지 49→49   부여박물관 44→44
```

**최대 +1점.** 「상황」 축 가중치가 0.10이고 그 안에 항목이 4개라 하나가 빠져도 거의 티가 안 난다.

즉 **이 결정은 점수 문제가 아니라 정직함 문제다.** 「본다」고 화면에서 말해 놓고 한 번도 채운 적이 없는 항목을 목록에 두느냐 마느냐.

### 4.3 Layer C — 6곳 중 1곳뿐

```
무령왕릉만 열린관광지 (2023년 지정), 나머지 5곳 인증 없음
효과: 54점 → 57점 (보정 1.04배), 라벨은 「주의」 그대로
```

인증을 못 찾은 게 아니라 **찾았는데 안 넣었다.** 확인된 인증이 전부 방문자센터·화장실 같은 **부속 건물**에 대한 것이라, 넣으면 「화장실이 인증받았으니 관광지 점수를 올린다」가 된다.

### 4.4 신고 권한 — 4라운드 검증에서 나온 새 사실

`anon`에게 신고를 열어 둔 것의 결과가 **생각보다 나빴다.** 관리자 화면은 200건 상한에 페이지 넘기기가 없다. 신고 264건 상태에서 실측:

```
상위 200행 = 전부 신고된 행
신고 안 된 제보의 첫 위치 = 없음(NULL)
```

**전부 신고하면 정렬 신호만 죽는 게 아니라 기본 화면에서 신고되지 않은 제보를 전부 밀어낸다.** 운영자가 「최신순」으로 바꾸지 않는 한 새 제보를 하나도 못 본다.

### 4.5 다섯 개 다 「B」를 권한 이유

우연이 아니다. 전부 같은 원칙이다 — **작동하지 않는 기능을 켜 둔 채로 두는 것보다 없다고 말하는 편이 정직하다.** 이 서비스가 「정보 없음」을 숨기지 않고 세어서 보여주는 것과 같은 원칙이다.
