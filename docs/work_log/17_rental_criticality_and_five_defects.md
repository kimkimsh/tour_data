# 17 — 대여를 판정에서 내리고, 16번이 남긴 다섯을 닫았다

16번은 남은 것을 두 줄로 정리했다 — **사람이 정할 것 하나**(대여 항목이 critical), **안 고친 판정기 결함 다섯**. 이 회차는 그 둘을 다 닫았다.

---

## 1. 대여는 수단이고, 방문자는 이미 결과를 들고 온다

### 1.1 증상

`MATRIX`에서 `wheelchair`는 P1a에, `stroller`는 P3에 **critical**이었다. 그런데 그 두 조건이 화면에 내거는 문구는 이렇다.

```
휠체어를 이용해요        ← 이미 타고 있다
유아차와 함께 가요       ← 이미 밀고 있다
```

대여가 없다고 **확인되면** 「다른 곳 권장」이 나간다. 자기 휠체어로 온 사람에게, 대여소가 없다는 이유로.

실측된 한 곳이 있었다.

```
서동공원과 궁남지 / 유아차 동반  →  대체추천
유일한 차단 항목: stroller       근거: 「유모차 대여 여부 - 없음」
```

### 1.2 v7이 이미 편 논리다

14번이 `elevator`를 critical에서 내릴 때 쓴 문장이 그대로 적용된다 — 엘리베이터는 층을 옮기는 **수단**이고, 방문자가 원하는 것은 보고 싶은 곳에 닿는 **결과**다. 대여도 같다. 휠체어를 **갖는** 수단이고, 방문자는 이미 갖고 왔다.

### 1.3 고침과 그 값

`wheelchair` P1a `C` → `S`, `stroller` P3 `C` → `S`. 점수에는 그대로 들어가고 화면에도 그대로 보인다. **판정을 혼자 결정하지 못하게 됐을 뿐이다.**

**골든 30건에서 라벨도 점수도 한 자리 안 움직였다.** 움직인 것은 `requiredCodes` 목록과 `layerB`뿐이다.

실제 데이터에서 움직인 것은 P3 하나다.

| 조건 | 전 | 후 |
|---|---|---|
| P1a 휠체어 이용 | 주의 9 · 방문가능 3 · 정보없음 1 | **그대로** |
| P3 유아차 동반 | 주의 6 · 방문가능 6 · **대체추천 1** | 주의 3 · 방문가능 10 · **대체추천 0** |

대체추천 1곳이 사라지고, 4곳이 주의 → 방문가능으로 올라갔다. 그 4곳이 올라간 이유는 **대여 정보가 `unknown`이었기 때문**이다 — 「빌려주는지 모른다」가 「주의」를 띄우고 있었는데, 자기 유아차를 가진 사람에게 그건 물어볼 일이 아니다.

### 1.4 이 변경이 드러낸 것 — 고치지 않았다

**P3의 critical이 이제 `restroom` 하나뿐이다.** 판정 전체가 장애인 화장실 한 항목 위에 선다.

유아차에게 계단과 단차는 휠체어만큼 문제인데 `access_route`·`entrance_passage`·`path_continuity`가 P3에서 전부 `S`다. 이건 이번 결정과 **별개의 표 문제**이고, 범위 밖이라 손대지 않았다. `docs/spec/06_suitability.md` §4.3에 적어 뒀다.

## 2. 판정기 결함 다섯

### 2.1 「안 합니다」가 「이용 가능」이었다 — 가장 위험했던 것

```
휠체어 대여 안 합니다   →  supported
휠체어 대여 안 해요     →  supported
대여 안 한다            →  supported
```

`NEGATION`의 단형 부정이 `안\s*[함됨돼되]`였다. **`합니다`·`해요`·`한다`의 첫 음절이 목록에 없었다.** 부정이 통과하면 맨 `대여`가 긍정 근거로 충분해서 그대로 「이용 가능」이 됐다.

음절 집합을 `[함됨돼되해하합한]`으로 넓혔다. `실내 안내판 있음`이 `안` + `내`라서 안 걸리는 것은 회귀로 박아 뒀다.

### 2.2 「예정」이 「있음」이었다

```
휠체어 대여 예정      →  supported
엘리베이터 설치 예정  →  unknown     ← 이쪽만 운 좋게 안전했다
```

엘리베이터가 안전했던 건 `설치 예정`에 걸릴 긍정 어간이 없어서일 뿐이다. `대여`는 어간이라 걸렸다.

`FUTURE_PLAN = /(예정|추진\s*중)/`을 넣고 `NEEDS_CHECKING` 옆에 뒀다 — 부정 **아래**, 긍정 **위**. `unsupported`가 아니라 **`unknown`**이다: 자료는 온다고 적었고, 그 사이에 왔는지 우리는 모른다.

### 2.3 `path_continuity`가 경로 파일만 있으면 「일부 가능」을 냈다

항목의 계약은 **「모든 필요 지점이 조건부로 도달 가능」**이다. 그런데 파생 문장 자신이 이렇게 적는다.

```
안내 경로 5단계 중 주의 표시 0개. 이 경로 밖의 구간은 확인하지 않았습니다.
```

확인하지 않은 것은 **조건부 도달이 아니라 도달 여부 모름**이다. `partial` → `unknown`.

덤으로: `partial`은 **확인된 항목 수를 늘려** 데이터 신뢰도를 올리고 있었다. 확인 안 한 것으로 신뢰도가 오르는 경로였다.

**오늘 바뀌는 행은 0개다.** 13곳 전부 `path_continuity`가 `curated`라 손으로 쓴 값이 이긴다. 막은 것은 앞으로 경로 파일을 하나 더 넣는 날이다 — 15번 §1과 같은 모양의 구멍이 한 칸 아래에 남아 있었던 셈이다.

### 2.4 기상 항목이 만료되지 않았다

나머지 27개 항목은 **건물**을 설명한다. 두 번 방문 사이에 변하지 않는다. 이 세 개는 **한 순간**을 설명한다.

최신성(`freshness`)은 이걸 못 덮는다. 신뢰도를 깎을 뿐 **상태는 그대로 세워 둔다.** 그래서 보존된 스냅샷이 90일까지 만점 구간으로 「발효 중인 기상 특보가 없습니다」를 계속 말했다 — 지나간 날에 대한 이상 없음 통보다.

```ts
export const CONTEXT_VALIDITY_DAYS = {
  weather_warning: 1,     // 오늘에 대한 진술
  weather_forecast: 1,
  crowd_forecast: 30,     // 자기 문장이 「향후 30일 예측」이라 적는다
};
```

창을 넘기면 `unknown`이 된다. **날짜가 없는 context 값도 만료로 친다** — 지금에 대한 주장인데 날짜가 없으면 아무도 그것을 놓을 수 없다.

**점수와 화면 양쪽에 적용했다.** 점수에만 걸면 배지는 「이상 없음」이라 하고 판정은 이미 그걸 세지 않는 상태가 된다 — 한 화면에서 한 질문에 두 답이다.

`isStaleContext()` 하나를 `normaliseFacts()`와 `CapabilityEvidence` 둘이 부른다. 회귀 6건, 규칙을 끄면 5건이 빨간불이 된다.

### 2.5 쉬운 글이 이야기 단위가 아니었다

```ts
readEasyScript(poi.slug, locale)   // 관광지 · 로케일
```

한 장소의 **모든 이야기가 같은 파일**을 받는다. 공산성에는 이야기가 여덟 개인데, 쉬운 글을 하나 쓰는 순간 여덟 개 전부가 같은 글을 자기 것이라고 달고 나온다.

파일 이름을 화면이 이미 쓰는 키에 맞췄다.

```
content/docent-easy/{slug}.{locale}.{odiiTid}-{odiiStid|seq}.md
```

**지금 쉬운 글이 0개라 옮길 것이 없다.** 스펙 두 곳(`04_data_model.md`, `05_ingest.md`)도 같이 고쳤다.

### 2.6 의견이 갈렸던 것 — 고치기로 했다

```
경사가 완만하여 휠체어 이동 가능   →  unknown
```

16번에서 「모호한 장벽이 긍정 판정을 막는 규칙은 `계단으로만 이동 가능`을 막으려고 일부러 넣은 것」이라 그대로 뒀다. **다시 보니 그 규칙을 건드릴 필요가 없었다.**

`완만`은 경사가 **장벽이 아니라는 진술**이다. `경사로`가 이미 같은 이유로 장벽 목록에서 빠져 있다 — 경사로는 시설이지 장벽이 아니라서. `완만한 경사`도 같다.

`GENTLE_MODIFIER = /^완만/` 하나를 토큰 주사에 넣었다. 장형 부정이 뒤에 오면 뒤집힌다.

```
경사가 완만하여 휠체어 이동 가능   →  supported
경사가 완만함                      →  supported
경사가 완만하지 않음               →  unsupported
계단으로만 이동 가능               →  unsupported   ← 그대로
```

`계단으로만`은 모호 규칙이 아니라 **배타 조사**가 잡는다. 둘은 애초에 같은 경로가 아니었다.

## 3. 실측

```
회귀 테스트        120건 (16번 111 → 120)
전체              269 통과 (16번 254 → 269)
골든 30건         라벨 0 변화 · 점수 0 변화
실제 KTO 문장 41개  판정 변화 0
e2e               42 통과 (production build + axe 2주사)
typecheck / lint / validate:content / check:contrast   전부 통과
브라우저 순회      15경로 × 1280px·390px — 콘솔 오류 0, 가로 넘침 0
```

돌연변이 검사로 새 규칙 넷이 전부 빨간불이 되는 것을 확인했다 — 단형 부정 음절 집합(5건), `FUTURE_PLAN`(3건), `GENTLE_MODIFIER`(2건), context 만료(5건).

**fixtures의 context 항목은 이제 기본값이 「오늘」이다.** 한 날짜를 공유했더니 `facts('supported')`라고 이름 붙은 케이스가 전부 조용히 그 뜻을 잃었다 — 케이스가 다루려던 것과 아무 상관 없는 이유로. 야간 수집은 어차피 매번 오늘 것을 쓴다. 날짜를 재는 두 케이스(`stale-data`, 최신성)는 명시적으로 지정한다.

## 4. 남은 것

**16번 §8에 적힌 것 중 셋이 그대로 남았다** — 전부 바깥에서 받아와야 닫힌다.

| 무엇 | 왜 |
|---|---|
| 부여 나성 좌표 | 핀과 왕릉원 매표소가 2,108m. 「능산리 산15-1」은 산 지번이라 지오코딩이 안 된다 |
| NVDA 수동 검증 | Windows가 필요하다. axe는 검사항목의 30~50%만 본다 |
| 음성 해설 항목 | 13곳을 채울 출처가 없어 (a)안은 못 한다. (b)안(안내 한 줄)은 들어가 있다 |

**그리고 이번에 드러난 것 하나** — P3의 critical이 `restroom` 하나뿐이다(§1.4).

**배포 전에 해야 할 것:** `pnpm ingest`. 판정기 변경(§2.1·2.2·2.6)과 `path_continuity` 변경(§2.3), 그리고 파생 항목의 `verifiedAt` 규칙이 **스냅샷에 반영되려면 수집이 한 번 돌아야 한다.** 지금 배포하면 코드만 새것이고 데이터는 옛것이다.
