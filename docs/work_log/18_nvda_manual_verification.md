# 18 — 눈에는 벌어져 있고 귀에는 붙어 있던 자리

17번은 대여를 판정에서 내리고 16번이 남긴 다섯을 닫았다. 그리고 「NVDA 수동 검증 — Windows가 필요하다」를 열린 항목에 다시 적었다. 05번이 그 줄을 처음 쓴 회차이고, 그 뒤로 09·10·11·12·15·17이 같은 줄을 이월했다. **이 회차는 그것을 실제로 돌린 회차다.**

**가장 중요한 결과 한 줄:** 이 서비스가 내놓는 단 하나의 답인 **판정이, 바로 뒤 낱말과 붙어서 읽히고 있었다.** 화면에는 「방문 가능」과 「휠체어 이용 기준」이 떨어져 있고, 스크린리더에는 「방문 가능휠체어 이용 기준」 하나로 들어갔다. 마스트헤드·긴급 연락처·목록 카드·상세 판정·근거 표·도슨트 재생 시간·안전시설 거리까지 **18종**이 같은 모양이었다.

이 결함은 **기존 검사 어느 것으로도 볼 수 없었다.** axe는 접근 가능한 이름이 비어 있지 않으면 통과시키고, 이 이름들은 비어 있지 않았다. 브라우저 순회도 못 본다 — 간격은 정확히 그려져 있었다. 소리로 들어야만 나온다.

## 1. 무엇으로 돌렸는가

NVDA 2026.2 포터블 + Chrome + Windows 11. 설치본을 만들지 않고 포터블 복사본을 `--create-portable-silent`로 떴다.

두 가지를 바꿔서 자동화 가능하게 만들었다.

| 설정 | 값 | 왜 |
|---|---|---|
| 합성기 | `silence` | 소리를 내지 않는다. 발화는 합성기에 가기 **전에** 기록되므로 전사본은 그대로 남는다 |
| 로그 수준 | `IO` (12) | `speech.speak()`가 `Speaking [...]`를 이 수준에 남긴다 |

키 입력은 OS 레벨이어야 했다. CDP로 주입한 입력은 DOM 기준으로는 성립하지만 OS 입력 큐를 거치지 않아 NVDA가 보지 못한다. `keybd_event`로 보내되 화살표·Insert·Home/End는 **확장 키 플래그**를 붙였다 — 빼면 넘패드 쌍둥이가 전달되고 NVDA는 그걸 전혀 다른 명령으로 읽는다.

### 1.1 Say All은 버렸다 — 페이지가 끝난 줄 알았다

처음에는 `NVDA+아래쪽 화살표`(전체 읽기)로 한 화면을 통째로 받으려 했다. 홈 화면이 예시 자료 배너에서 멈췄다. 화면이 거기서 끝나는 것처럼 보였지만 **HTML에는 체크상자 6개와 `fieldset` 2개가 그 아래에 있었다.**

`silence` 합성기가 인덱스 콜백을 제대로 올리지 않아 전체 읽기가 중간에 멎은 것이다. **사이트 결함이 아니라 내 하네스 결함이었다.** 아래쪽 화살표로 한 줄씩 걸으니 45줄이 전부 나왔다. 이후 전 구간을 줄 단위 걷기로 바꿨다.

같은 자리에서 하마터면 「홈 화면이 조건 폼을 읽어 주지 않는다」를 결함으로 적을 뻔했다.

## 3. 원인 — CSS `gap`은 텍스트가 아니다

전부 한 뿌리다. 이 자리들은 플렉스·그리드의 `gap`, 마진, 또는 블록 쌓기로만 떨어져 있다. 그 간격은 **그려지는 것이지 문서에 적히는 것이 아니다.** 접근 가능한 이름 계산과 스크린리더의 줄 조립은 둘 다 찾은 텍스트를 그대로 이어 붙인다.

공백을 넣으면 되는 문제가 아니었다. `DocentView.tsx`에는 **이미 `{' '}`가 있었고** HTML에도 공백이 실제로 찍혀 있었다.

```
재생 시간<!-- --> <span class="tabular">2분 4초</span>
```

그런데도 「재생 시간2분 4초」로 읽혔다. **Chrome이 공백만으로 된 텍스트 노드를 접근성 트리에 넣지 않기 때문이다.**

### 3.1 구분자 후보를 재어 봤다

같은 줄을 다섯 가지로 만들어 NVDA에 읽혔다.

```
구분자 없음              →  방문 가능휠체어 이용 기준
{' '}                    →  방문 가능휠체어 이용 기준
.sr-only 안에 일반 공백    →  방문 가능휠체어 이용 기준
.sr-only 안에 U+00A0      →  방문 가능\xa0휠체어 이용 기준
.sr-only 안에 쉼표         →  방문 가능,휠체어 이용 기준
```

**일반 공백은 세 형태 전부 사라진다.** 살아남는 것은 무중단 공백과 문장부호뿐이다.

쉼표를 골랐다. 이 둘은 서로 다른 사실이고, 「방문 가능 휠체어 이용 기준」을 한 호흡으로 들으면 §2.2가 적은 그 명사구가 **조용해졌을 뿐 그대로** 남는다. 쉼이 뜻을 나른다.

**대가는 명시한다.** NVDA 한국어 기호 사전에서 쉼표는 `most` 수준에 `preserve always`다. 기본 수준은 `some`이므로 합성기에는 쉼으로 전달되고 낱말로 읽히지 않는다. 기호 수준을 올려 둔 사용자는 「콤마」를 듣는다.

## 5. 검사로 만들려다 — 아무것도 안 보는 검사를 먼저 썼다

`tests/e2e/spoken-names.spec.ts`를 Playwright의 `ariaSnapshot()`으로 썼다. 9건 전부 통과했다.

그다음 `SiteHeader.tsx`의 구분자를 **일부러 빼고** 다시 빌드해서 돌렸다. **여전히 9건 전부 통과했다.**

원인은 이렇다. Playwright는 접근 가능한 이름을 **명세대로** 계산하고, 명세는 블록 레벨 자손 사이에 공백을 넣는다. Chrome은 넣지 않는다. 그리고 NVDA가 읽는 것은 Chrome이다. 그래서 `ariaSnapshot()`은 구분자가 있든 없든 마스트헤드를 「모두의 백제 Gongju · Buyeo」라고 보고한다.

**명세를 지키는 구현이 실제 동작을 가렸다.** 10번이 「성공했다고 보고하는 실패」라고 부른 것과 같은 모양이고, 이번에는 내가 그것을 새로 하나 만들었다.

`textContent`로 바꿔 다시 썼다. Chrome과 똑같이 이어 붙이기 때문이다. `aria-hidden` 요소는 먼저 떼어 낸다 — 낭독에서 빠지는 것들이고, 두면 배지 글리프가 결함처럼 보인다. 같은 변이로 다시 돌려 **빨간불이 되는 것을 확인했다.**

### 5.1 패턴 규칙은 넣었다가 뺐다

「한글 뒤에 라틴 문자나 숫자가 바로 오면 결함」이라는 규칙을 같이 넣었다. 세 가지를 새로 잡아냈다.

```
우리가 더한 항목content/facilities.json
공주중동성당TarRlteTarService1
매우 높음detailWithTour2.handicapetc
```

**NVDA는 이 셋을 한 번도 한 덩어리로 읽지 않았다.** 전사본 안에서 0건이다. 각각 다른 블록이고 스크린리더는 블록을 다른 줄로 읽는다. `textContent`에는 줄바꿈이 없어서 그 경계를 볼 수 없었을 뿐이다.

동시에 이 규칙은 **가장 나쁜 자리를 볼 수 없다.** 「방문 가능휠체어 이용 기준」은 한글과 한글이고, 그것을 보통 문장과 가르는 문자 규칙은 없다.

맞는 페이지에서 울리는 검사는 꺼진다. 그래서 뺐다. 남긴 것은 **실측한 문자열의 목록**이다. 새 자리는 이번처럼 발화 로그를 읽어서 찾고, 찾으면 목록에 더한다.

## 6. 잘 되고 있던 것 — 특히 하나

과업 A·B·C가 확인한 것 가운데, **이미 맞게 되어 있던 것을 적는다.** 고칠 것만 적으면 무엇이 검증됐는지 다음 사람이 알 수 없다.

### 6.1 라이브 리전이 읽힌다

15번 §9가 이렇게 적었다 — 「axe 42경로가 통과하지만 **라이브 리전이 실제로 읽히는지 들어 본 사람이 없다.**」

들었다. 조건을 하나씩 고를 때마다 이렇게 나왔다.

```
선택: 휠체어 이용
선택: 휠체어 이용, 오래 걷기 어려움
선택: 휠체어 이용, 오래 걷기 어려움, 눈이 잘 안 보임
```

06번 A-4가 고친 「언마운트되지 않는 `role="status"`」가 실제로 작동한다. **이 줄은 이제 닫힌다.**

### 6.2 제보 폼의 오류가 스펙대로 동작한다

빈 채로 제출하면 이렇게 들린다.

```
엘리베이터 고장 | 라디오 버튼 | 체크 안 함 | 무엇이 문제인지 하나 골라 주세요. | 8개 중 1번째
알림 | 무엇이 문제인지 하나 골라 주세요.
```

포커스가 문제 필드로 옮겨 가고, `aria-describedby`로 한 번, `role="alert"`로 한 번 읽힌다. [12번 §3](./12_audit_and_score_removal.md)이 고친 「`getElementById`가 React 커밋 전에 돌아 포커스를 못 옮기던」 것이 실제로 옮겨지는 것을 들었다.

## 7. 확인하지 못한 것

**지도 마커를 보지 못했다.** 이 환경에 지도 키가 없어 지도가 뜨지 않았고, 화면은 「지도를 불러오지 못했습니다. 위 목록만으로도 모든 기능을 쓸 수 있습니다.」를 읽었다. 대체 문구가 제대로 읽힌다는 것은 확인했지만, 마커가 실제 DOM 링크로 이름과 함께 읽히는지는 **확인하지 못했다.** [11번 §8](./11_redesign_map_scoring_pois.md)이 적은 「마커 자체는 접근 가능한 이름을 가진 실제 `<a>`로 만들었지만 **검사로 증명한 것이 아니다**」는 그대로 열려 있다.

과업 C의 문장은 「지도를 붙였을 때 그 **아래·위의 목록**이 계속 읽히는지, 제보 폼 라벨이 읽히는지」다. 그 둘은 확인했다. 마커는 그 문장에 없고, 별도 항목으로 남는다.

### 7.1 고치지 않은 것 셋

| 무엇 | 왜 안 고쳤나 |
|---|---|
| 출처 줄의 링크 이름이 주소 그대로 | `https://access.visitkorea.or.kr/ms/detail.do?cotId=e9a2d704-…`가 통째로 읽힌다. 길지만 **보이는 글자가 그것**이고, 인용 표기를 바꾸는 것은 §3.3 표기 규칙 문제다. 범위 밖이라 손대지 않았다 |
| 이따금 들리는 「클릭 가능」 | 역할 없는 요소에 클릭 핸들러가 붙었을 때 NVDA가 붙이는 말이다. 어느 요소인지 특정하지 못했다 |
| 조건 선택 시 라이브 리전이 체크상자 상태보다 **먼저** 읽힘 | 「선택: 휠체어 이용」이 「체크함」보다 앞선다. 위반은 아니고, 리전과 상태 변화가 서로 다른 사건이라 순서를 강제할 자리가 없다 |

## 9. 남은 것

| 무엇 | 왜 |
|---|---|
| **지도 마커의 스크린리더 검증** | 지도 키가 있는 환경에서 해야 한다. 11번 §10.1부터 열려 있다 |

| **음성 해설 항목** | 17번 그대로. 13곳을 채울 출처가 없어 (a)안은 못 한다 |
| 「클릭 가능」이 붙는 요소 특정 | §7.1 |

`common.honesty.a11ySelfCheck`는 ko·en 모두 NVDA 절을 포함하는 형태로 되돌렸다. 09번 §1이 스펙 `08_accessibility_legal.md` §1.5에 넣어 둔 **조건부 문구 규칙이 발동한 것**이고, 같은 자리에 「조건 충족」과 지도 마커 예외를 적어 두었다. 되돌리지 않는다.

**배포 전에 해야 할 것은 없다.** 이 회차는 화면 마크업과 검사만 건드렸고 수집 자료를 건드리지 않았다.
